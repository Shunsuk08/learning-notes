## Tier S：データベースの基礎（#11）— 最優先

**なぜ最優先か**：「知識として知っている」と「実務で事故らない」の差が最も出やすく、ローカルにMySQL/PostgreSQLを立てて自分で検証できるため独学と相性が良い。

### 正規化／非正規化の判断基準
**用語解説**：正規化＝同じ情報を複数箇所に重複して持たないようにテーブルを分割する設計手法。非正規化＝あえて重複を許し、JOINを減らして検索を速くする手法。
- 正規化のメリット：更新の一貫性、拡張のしやすさ。デメリット：JOINが増えて検索性能が落ちる
- 非正規化のデメリット：更新時に複数レコードを直す必要が生じる（例：所属企業名を全レコードに持たせると企業名変更時に全件更新）
- **鉄則**：「あとで非正規化すればいい」という後付け対応が最も不適切。初期設計時に非正規化すべき理由を整理しておく

### インデックス設計
**用語解説**：インデックス＝本の索引のように、特定の列の値からレコードを高速に探せるようにする仕組み。カーディナリティ＝列の値の種類の多さ（会員IDは高カーディナリティ、性別は低カーディナリティ）。
- カーディナリティが高い列ほどインデックスが効きやすい（100万件中カーディナリティ80万なら絞り込み後は少数行、カーディナリティ2なら平均50万行残りほぼ効かない）
- 複合インデックスは高カーディナリティ列を前方に置くのが基本原則。ただし機械的に適用せず、実際のクエリパターン(WHERE句の組み合わせ)で検証する
- **やること**：EXPLAINで実行計画を読み、想定した索引が実際に使われているか確認する習慣をつける

### トランザクション分離レベル
**用語解説**：トランザクション＝複数の処理をひとまとまりとして「全部成功」か「全部失敗」にする仕組み。分離レベル＝複数の処理が同時に走ったときにお互いの影響をどこまで防ぐかの設定。
- READ UNCOMMITTED（何も防がない）／READ COMMITTED（汚れたデータの読み取りだけ防ぐ）／REPEATABLE READ（読み取り中の値のブレも防ぐ）／SERIALIZABLE（全部防ぐが遅い）
- **ロストアップデート対策**：分離レベルだけに頼らず、金銭・在庫のような重要データの更新では`SELECT ... FOR UPDATE`のような明示的ロックを併用する
- 注意：MySQLのデフォルトはREPEATABLE READ、PostgreSQLのデフォルトはREAD COMMITTEDと異なる

### N+1問題とORMの限界（JPA/Hibernate、SQLAlchemy）
**用語解説**：N+1問題＝一覧を取得する1回のSQLの後、関連データを1件ずつ追加でN回SQLを発行してしまう非効率な状態。ORM＝オブジェクトとDBのテーブルを対応づけて、SQLを直接書かずにデータ操作できるようにするツール。
- JPAのデフォルトのフェッチ戦略は非対称：`@ManyToOne`はEAGER（即座に読み込む）、`@OneToMany`はLAZY（必要になるまで読み込まない）——これを知らずに使うと事故る
- 対策：①エンティティ設計時はLAZYを基本にする②`JOIN FETCH`で1つのSQLにまとめる③それでも解消できなければネイティブSQLに降りる

### マイグレーション設計
**用語解説**：マイグレーション＝DBのテーブル構造（スキーマ）をバージョン管理しながら変更していく仕組み。
- DDL（テーブル定義変更）のアルゴリズムにはロックの有無に差がある（`INSTANT`＝ロックなし／`INPLACE`＝更新は許可／`COPY`＝更新禁止）。これをCIで検知すると安全
- `lock_wait_timeout`（MySQLのデフォルトは1年）を数秒に短縮しておくと、ロック待ちによる障害を未然に防げる

## Tier S：SOLID設計原則（#1）

**用語解説**：SOLIDはS(単一責任)・O(開放閉鎖)・L(リスコフの置換)・I(インターフェース分離)・D(依存性逆転)の5原則の頭文字。
- 抽象論で終わらせず、「このインターフェースは肥大化していないか」「このクラスは複数の理由で変更されうるか」をレビューの具体的指摘として言語化できることが実務レベル
- メルカリのリファクタリング実例：ISP（インターフェース分離）違反を、①参照箇所の特定→②クライアント別インターフェース定義→③依存先置き換え→④テストスタブ対応→⑤旧参照削除→⑥旧定義削除、という段階的な手順で安全に解消

## Tier A：分散システムの基本・冪等性（#15）

**用語解説**：冪等性＝同じ処理を1回実行しても複数回実行しても結果が変わらない性質。分散システムの多くは通信の欠落を避けるため「少なくとも1回は実行する（at-least-once）」を前提にしており、受信側を冪等にする設計が現実的な対応。
- 実装パターン例（Timee社）：請求レコードに「締め前／締め中／締め後」の状態フラグを持たせ、リトライ時に処理済みレコードをスキップする。副次効果としてバッチ処理全体の完了時間も短縮された
- **対象者への接続**：現案件のGenesys Cloud API連携・バッチ処理のような外部API連携の文脈に直結。実務の中で優先的に触れられる

## Tier A：主要なデザインパターン（#12）

**用語解説**：デザインパターン＝よくある設計上の問題に対する定石的な解決策のカタログ。ファクトリー（オブジェクトの生成方法を隠蔽）、デコレーター（機能を後から追加）、シングルトン（インスタンスを1つに限定）、オブザーバー（状態変化を他に通知）など。
- SOLID原則・クリーンアーキと語彙が接続する（例：依存性逆転の原則を実現する手段としてファクトリーパターンを使う）
- ドメイン駆動設計（DDD）学習の前段としても有効

### 参考：クリーンアーキテクチャ／レイヤード／ヘキサゴナルの違い
- 3つの呼び名の違いに振り回されず、「関心の分離」と「依存性のルール」という共通原理で自分のプロジェクトの構造を説明できることが重要（呼び名自体は本質ではない、という指摘が技術記事にある）
- 対象者はPythonでクリーンアーキの「型」（フォルダ構成）はすでに到達済みと推測される。次の一歩は、Entitiesレイヤーに**値オブジェクト・集約**というDDDの語彙を導入し、UseCase層が複数集約をまたぐビジネスルールの調整役になっているかを検証すること

## Tier B：API設計とバージョニング（#10）

**用語解説**：べき等性＝同じリクエストを繰り返しても結果が変わらない性質（GET/PUT/DELETEはべき等、POSTは非べき等）。バージョニング＝APIの破壊的変更を、既存の利用者に影響を与えずに導入する方法。
- リソース単位でURIを設計し、HTTPメソッドの意味論を守る
- ページネーション・フィルタリング・ソート・ステートレス設計・一貫したエラーフォーマットが保守性と互換性を高める

## Tier B：テスト駆動開発 TDD（#2）
- 単体テストの実務経験はすでにあるため、「テストを先に書いてから実装する」型としての体系化が次の段階
- テストピラミッド（単体/結合/E2E）の各層で何をどこまで担保するかを自分の言葉で説明できるようにする

## Tier C：イミュータビリティと安全な状態管理（#5）
**用語解説**：イミュータブル（不変）＝一度作ったオブジェクトの状態を後から変更できないようにする設計。状態を持つオブジェクトを複数箇所で共有すると起きるバグ（意図しない書き換え）を防ぐ。
- Javaの`record`（不変クラスを簡潔に書ける言語機能）、Pythonの`dataclass(frozen=True)`等、モダン言語機能の学習と接続できる

## Tier C：パフォーマンスチューニング（#14）
- DB側（インデックス最適化、`SELECT *`回避、EXPLAIN確認、水平パーティショニング、コネクションプール設定）はTier Sのデータベース基礎と重複。アプリ側のプロファイリング（メモリ・レイテンシ・スループット計測）は実務機会が少なく後回しでよい

## 非機能要件の実装への落とし込み（補足）

### 例外設計・エラーハンドリング
- 正常系エラーは例外を使わずステータスコードで表現し、異常系のみ独自例外クラス（メッセージコード・ログレベル等の属性つき）で扱う
- 例外処理・ログ出力を基底クラスに統一し、各クラスでの個別実装を減らす（Javaのエラーハンドリング鉄板4箇条：①エラー分類②例外クラス定義③基底クラスでの一元処理④ログ出力の標準化）

### ロギング設計
- ログは「後から見返す記録」ではなく「監視・分析・改善の手段」として設計する。5W1Hに基づき過不足なく出力し、タイムスタンプはISO8601で統一、TRACE/DEBUG/INFO/WARN/ERRORの5段階を使い分ける
