# AWS / インフラ カリキュラム

自己開発アプリ`studymate-ai`（Java Spring Boot / React+TypeScript+Vite / PostgreSQL / Docker+ECS Fargate）を教材に、AWS/インフラ側の「一気通貫」力を積み上げるための学習マップ。優先度の根拠は[../reference/skill-priority-matrix.md](../reference/skill-priority-matrix.md)を参照。

用語は初出時に簡単な解説を付ける（前提知識なしで読める想定）。

## 「一気通貫」7フェーズ（インフラ/運用側）

Netflix「Full Cycle Developers」・CARTA・Qiita等の技術記事の横断調査（2026-09-21）から整理。**個人が全領域に精通する必要はなく、「意思決定・実行できる範囲を広げる」ことが本質**という留保つき。

### ①要件定義・非機能要件設計
**用語解説**：非機能要件＝「動くかどうか」ではなく「どれだけ落ちないか・速いか・安全か・安く運用できるか」を決める要件。
- AWS Well-Architected Framework 6つの柱（運用上の優秀性／セキュリティ／信頼性／パフォーマンス効率／コスト最適化／持続可能性）が業界標準の判断フレーム
- **やること**：可用性を99.9%→99.99%に上げると設計段階で数倍・運用開始後は10倍以上コストが増える、というようなトレードオフを言語化する練習

### ②アーキテクチャ選定・トレードオフ判断（ADR）
**用語解説**：ADR(Architecture Decision Record)＝「なぜこの技術・構成を選んだか」を後から追える形で残す文書。基本5要素は「タイトル・コンテキスト・決定・ステータス・結果」。
- Cybozuのシニアエンジニアの3原則：①事実と解釈とアクションを分ける（「技術的負債が溜まったからリファクタリング」は事実が抜けている）②最初に思いついた案をそのまま採用せず複数の選択肢を比較する③既存実装ではなく理想の構造から考える
- **やること**：studymate-aiのStage2（ECS or Lambda）の決定をADR形式で書き直してみる

### ③IaCでの環境構築
**用語解説**：IaC(Infrastructure as Code)＝サーバーやネットワークの構成をコードで管理し、再現可能にする手法。Terraformが代表的なツール。
- 実務記事の示唆：「手動構築での構成理解が先」——コンソール操作で仕組みを理解してからIaC化する順序が妥当（現在のStage1〜3→Stage4という順序と整合）
- **現在地**：Terraformは読解のみで実装経験なし。Stage4がここに該当

### ④実装
- 「自分のパッチを最後まで（テストからリリースまで）責任を持って書き切る」がフルサイクルの考え方の核

### ⑤CI/CD構築
**用語解説**：CI(継続的インテグレーション)＝コード変更のたびに自動でビルド・テストする仕組み。CD(継続的デリバリー/デプロイ)＝テストを通ったコードを自動で本番環境に届ける仕組み。
- ECS on Fargateでの実務レベルの要点（対象者のスタックにそのまま該当）：
  - デプロイ戦略の使い分け——**ローリング更新**（シンプルだが一時的ダウンリスクあり）／**ECSネイティブBlue/Green**（CodeDeploy不要、インスタントロールバック可能）／**CodeDeployのBlue/Green**（複雑なフック検証向け）
  - GitHub Actions OIDC認証：長期アクセスキーを置かず`role-to-assume`で一時クレデンシャルを取得する（鍵レス化）
  - CommitSHAタグでのイメージ版固定（`latest`依存を避ける）
  - **SIGTERMハンドラによるグレースフルシャットダウン実装**（コンテナ停止時に処理中のリクエストを安全に終える）
  - ECR脆弱性スキャンをCIの品質ゲートに組み込む

### ⑥監視・アラート設計（SLI/SLO）※Stage6で対応
**用語解説**：SLI(Service Level Indicator)＝実際に測る指標（例：成功リクエスト数／総リクエスト数）。SLO(Service Level Objective)＝その指標の目標値（例：月次99.9%）。
- 指標選定：平均値だけでなく分位点p50/p90/p95/p99を使い分ける（p99でSLO違反を検出しやすい）。レイテンシー計算クエリ確定→分位点算出→eCDF(累積分布)で分布を把握→目標値を決める、という流れ
- バーンレートアラーム（Google SRE手法）：1時間ウィンドウ（急激な悪化を検知）／6時間ウィンドウ／3日ウィンドウ（緩やかな劣化を検知）の3段階で設計
- **やること**：studymate-aiにCloudWatchで自分のSLI/SLOを定義し、閾値超過でアラートが飛ぶところまで作る

### ⑦障害対応・ポストモーテム／パフォーマンスチューニング ※Stage6で対応
**用語解説**：ポストモーテム＝障害の再発防止のために「何が起きたか・なぜ起きたか・今後どうするか」を構造化して書く振り返り文書。
- KAYACのSREチーム事例：1年半で25本以上のポストモーテムを書き、そこから設定不備を自動検出する内製ツールが生まれた——単発の反省文で終わらせず恒久対策のツール化まで持っていくのが一気通貫の到達点
- テンプレート構成：インシデント概要／インパクト／タイムライン／根本原因／トリガー／検知方法／対応の経緯／教訓／アクションアイテム
- **やること**：studymate-aiで意図的に障害（DB接続断など）を起こし、収束させ、このテンプレートでポストモーテムを書く

## Tier B/D の個別トピック

### セキュリティの基礎（Tier B, #7）
**用語解説**：TLS/SSL＝通信を暗号化する仕組み。JWT(JSON Web Token)＝ログイン情報などを安全にやり取りするための署名付きトークン。OAuth2＝「このアプリに自分の情報へのアクセスを許可する」ための認可の仕組み。
- Stage3（IAM, Secrets Manager, JWT等）がここに対応。AWS側（IAMの最小権限原則）とアプリ側（JWTの検証・OAuth2フロー）の両方を押さえる

### キャッシング戦略（Tier B, #9）
**用語解説**：キャッシュ＝よく使うデータを高速な場所に一時保存し、毎回DBに問い合わせなくて済むようにする仕組み。
- インメモリ（アプリ内キャッシュ）と分散キャッシュ（Redis/ElastiCache等、複数サーバーで共有）の違い、削除ポリシー（LRU等）の考え方

### ストリーミング/メッセージング（Tier D, #13）
**用語解説**：Kafka＝大量のイベントデータをリアルタイムでやり取りするための分散メッセージングシステム。キュー/Pub-Sub＝処理を非同期化し、システム間を疎結合にする仕組み。
- 現状のワークロードでは優先度低いが、現案件のGenesys Cloud API（WebSocketでのリアルタイム取得）はこの領域と概念的に近い。自社サへの移動を検討するタイミングで再評価
