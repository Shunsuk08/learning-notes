## 4. お客様との仕様調整術

> 会社資料の教材: 『入門 要件定義』『SEのためのヒアリング技術』『コンサル一年目が学ぶこと』
> **書籍の代わり**: 下の要約。前案件でPOレビューの再レビューをゼロにした「論点を先に整理してから持っていく」やり方が、そのまま土台になる。

### 調整の流れ

```
論点を洗い出す → 論点ごとに選択肢と推奨を作る → 確認する → 決まったことを記録する → 関係者に展開する
```

### 論点の持っていき方

悪い例:「エラー時の動きはどうしますか？」（相手が一から考えることになる）

良い例:
```
【論点】納付データの取込で、1件だけ形式エラーがあった場合の動き
【選択肢】①全件を取り込まない ②エラー行だけ飛ばして残りを取り込む
【現行】①の動き（現行の設計書 p.12）
【推奨】①（現行踏襲。②は部分取込の後始末が業務側に必要になる）
【決めてほしいこと】①で良いか。②にする場合は業務側の運用手順が要る
```

ポイントは3つ。**①相手が「はい／いいえ」か「①か②か」で答えられる形にする ②更改案件では「現行はどうか」を必ず添える ③自分の推奨と理由を言う**（推奨が無いと判断が遅れる）。

### 確認事項一覧（QA表）を回す

| No | 起票日 | 論点 | 選択肢・推奨 | 回答者 | 回答期限 | 回答 | 反映先（設計書・ソース） | 状態 |
|---|---|---|---|---|---|---|---|---|

- **回答期限を必ず入れる**（無いと永遠に返ってこない）
- 「反映先」まで埋めて初めて閉じる。回答をもらっただけで閉じると、設計書に反映し忘れる
- 公共系では、仕様を変えるには**変更管理の手続き**（変更依頼書・影響調査・承認）が要ることが多い。口頭で「いいですよ」と言われても、手続きを通すまで作り始めない

### 会議の後にやること

当日中に「決定事項／保留事項（誰が・いつまでに）／次回予定」を3行で送る。議事録が正式に回るのを待たない。

## 5. 静的解析（Coverity）

> 会社資料の教材: Coverity公式ドキュメント、CWE Top25、OWASP Top10、GitHub CodeQLドキュメント
> **書籍の代わり**: 下の要約 ＋ 以下（全部読まない。一覧の見出しだけ眺める）
> - [CWE Top 25（2025）](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html) / [OWASP Top 10（2025）](https://owasp.org/Top10/2025/) / [CodeQL ドキュメント](https://codeql.github.com/docs/)
> - Coverityの製品ドキュメントは製品ライセンス側で配布されていることが多い。参画後に案件内の資料を確認する

### 静的解析とは

プログラムを**動かさずに**ソースを解析し、バグになりそうな箇所を見つける。Coverityは、変数に入る値の流れ（データフロー）を追って「この経路だとnullのまま使われる」のような指摘を出すのが得意。

### よく出る指摘の種類（Javaの場合）

| 種類 | 例 | 典型的な直し方 |
|---|---|---|
| null参照 | `null` を返しうるメソッドの戻り値をそのまま使っている | null判定、Optional、例外にする |
| リソースリーク | `InputStream` や `Connection` を閉じていない経路がある | try-with-resources |
| 到達しないコード | 条件が常に偽で、通らない分岐がある | 条件の誤りを疑う（消すだけで済ませない） |
| 使われない値 | 代入したのに使っていない | 書き間違い（別の変数に入れるつもりだった等）を疑う |
| 汚染データ | 画面入力をそのままSQLやファイルパスに使っている | バインド変数、入力チェック |

### 指摘への対応の流れ（サブリーダーとして見るところ）

```
指摘 → 分類（本物のバグ／誤検知／意図どおり） → 対応方針を決める → 修正 or 理由を記録して抑止
```

- **「誤検知」「意図どおり」で閉じるときは、理由を必ず残す**。理由の無い抑止は、レビューで差し戻す
- 件数を減らすことが目的にならないようにする。同じ種類の指摘が多い場合は、規約や共通部品の問題（真因）を疑う → 項目6

## 6. 真因分析（5Why・なぜなぜ分析）

> 会社資料の教材: 『トヨタの問題解決』『なぜなぜ分析実践編』、Lean Enterprise Institute A3 Thinking資料、IPA「システム障害分析事例集」
> **書籍の代わり**: 下の要約 ＋ IPAの無料資料
> - [IPA 情報処理システム高信頼化教訓集 別冊II：障害分析手法（PDF）](https://www.ipa.go.jp/archive/files/000071988.pdf)
> - [IPA 近年のソフトウェア障害事例の分析により得られた教訓例（PDF）](https://www.ipa.go.jp/archive/files/000057669.pdf)

### 直接原因と真因

- **直接原因**: そのバグを直接引き起こしたもの（例: nullチェックが漏れていた）
- **真因**: それを生んだ仕組みの穴（例: 共通部品がnullを返す仕様なのに、設計書に書かれていなかった）

直接原因だけ直すと、**同じ種類のバグがまた出る**。真因を直すと、同じ種類のバグがまとめて減る。

### 5Whyのルール

1. **事実から始める**。「たぶん〜だった」は書かない。推測が混じったら、確かめてから次に進む
2. **人で止めない**。「担当者の注意不足」「確認漏れ」で止めたら、「なぜ注意不足でも気づける仕組みが無かったか」とさらに掘る
3. **逆読みで検証する**。下から「〜だから、〜になった」とつなげて読み、論理が飛んでいないか確かめる
4. **対策は仕組みに打つ**。「気をつける」「周知する」は対策にならない。チェックリスト・自動テスト・静的解析ルール・設計書のテンプレートなどに落とす

### 例

```
事象: 結合試験で、所有者未登録の車両を表示すると500エラー
なぜ1: 所有者名がnullのまま toUpperCase() を呼んでいた
なぜ2: 実装者は「所有者は必ず登録されている」と思っていた
なぜ3: 設計書に「所有者は未登録のことがある」と書かれていなかった
なぜ4: 設計書のテンプレートに、項目ごとの「必須/任意」欄が無い
→ 真因: 設計書テンプレートに必須/任意の欄が無いこと
→ 対策: テンプレートに欄を追加し、既存の設計書も同じ観点で点検する
逆読み: 欄が無い → 書かれない → 実装者が必須と思い込む → nullを考慮しない → 500エラー（つながる）
```

このやり方は、前案件のCLAUDE.mdの「1件の指摘を、そのクラス全体の指摘として受け取る」と同じ考え方。

# 午後（手を動かす）: Todoアプリ（インメモリ版）

公式チュートリアルの「Todoアプリケーションの作成」を、**インフラストラクチャ層はインメモリ（Map）の実装**で進める。MyBatis3への置き換えはDay3でやる。

<https://terasolunaorg.github.io/guideline/current/ja/Tutorial/TutorialTodo.html>

### 進め方（日本語フローパイプ）

各クラスを書く前に、**処理の流れを日本語で3〜5行書いてから写経する**。書いた後に、日本語の各行がコードのどこに当たるかを対応させる。

例（`TodoServiceImpl#create` を書く前）:

```
1. 未完了のTodoの件数を数える
2. 上限（5件）以上なら業務エラーにする
3. IDと作成日時を振る
4. 保存して返す
```

### 写経する順番

1. ドメイン層: `Todo`（モデル）→ `TodoRepository` → インメモリの実装 → `TodoService` / `TodoServiceImpl`
2. アプリケーション層: `TodoForm` → `TodoController` → `list.jsp`
3. 一覧表示 → 新規作成 → 完了 → 削除 の順に、1機能ごとにビルドして画面で確かめる
4. 1機能できるごとに `git commit`

### 読みながら書くメモ（7カテゴリのうち4つ）

| カテゴリ | 探すもの |
|---|---|
| ①構造 | どのクラスがどの層にあるか。Day1の図と合っているか |
| ②データ整合性 | `@Transactional` がどこに付いているか。なぜControllerではなくServiceか |
| ③信頼性 | 業務エラー（未完了の上限超え）がどこで投げられ、画面にどう出るか |
| ⑥セキュリティ | `<form:form>` にCSRFトークンが自動で入っているか（画面のHTMLソースで確認） |

### 改造課題（写経が終わったら）

1. 未完了の上限を5件から3件にする。**どのファイルを何行変えたか**を `git diff` で確認する
2. タイトルが空のとき、画面にエラーが出ることを確かめる。どのアノテーションが効いているか探す
3. 完了済みのTodoをもう一度「完了」にしようとしたら何が起きるか、コードを読んで予想してから試す

## 確認問題

**Q1.** お客様に「画面の日付は和暦にしますか？」と聞こうとしている。項目4の型で論点を書き直せ。

<details><summary>答えの例</summary>

【論点】一覧画面の日付表示の形式 【選択肢】①和暦（令和8年10月1日）②西暦（2026/10/01）【現行】①（現行画面のキャプチャ添付）【推奨】①（現行踏襲。利用者の慣れを優先）【決めてほしいこと】①で良いか。②にする場合は帳票も合わせるか。
</details>

**Q2.** 結合試験で「ログインユーザー名がnullで落ちる」バグが3件続いた。3件とも担当者が別。5Whyの1段目と、掘る方向を書け。

<details><summary>答えの例</summary>

1段目は事実:「3件とも、ログインユーザー情報を取得する共通処理の戻り値をnullチェックせずに使っていた」。担当者が別なのに同じバグ＝**人ではなく共通の仕組みに原因がある**サイン。共通処理の仕様（nullを返すことがあるのか）、その仕様が設計書・規約に書かれているか、静的解析で検出できなかったのはなぜか、の方向に掘る。
</details>

**Q3.** `@Transactional` をControllerではなくServiceに付ける理由を説明せよ。

<details><summary>答え</summary>

トランザクションの範囲は「業務として一まとまりで成功／失敗させたい処理」で、それを知っているのはドメイン層のService。Controllerは画面の入出力の担当で、業務の境界を知らない。複数のDB更新を「全部成功か、全部取り消し」にする単位をServiceのメソッドに揃える。

注意: `@Transactional` を付けても、**2人が同時に作成したときに「件数チェック→保存」の間に割り込まれる問題は防げない**（標準の分離レベルでは）。それには行ロックや一意制約などの排他制御が別に要る。
</details>
