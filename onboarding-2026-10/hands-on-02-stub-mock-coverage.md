## Phase 1: ライブラリ無しで概念を掴む

**なぜライブラリを使わないか**: Mockitoの `when(...).thenReturn(...)` は便利すぎて、「何が起きているのか」を隠してしまう。前の案件で分からなかったのは、たぶんここ。自分で書くと **「スタブって、ただのクラスじゃん」** で終わる。

### 1-1. スタブ・フェイク・モック・ダミー

```bash
cd ~/git/learning-notes/onboarding-2026-10/exercises/test-drill
java StubMockDrill.java
```

**先にファイルを読んで、各テストがOKかNGか予想してから実行する。**

ファイルの中身は4種類のニセモノ。全部ただのクラスで、特別なものは何もない。

| 種類 | 中身 | 何を確かめるのに使うか |
|---|---|---|
| **スタブ** | `return 固定値;` と書いただけのクラス | 戻り値が正しいか（**状態の検証**） |
| **フェイク** | `Map` で動く簡易実装 | idごとに違う値を返せる。本物に近い |
| **モック** | 呼ばれた内容を `List` に記録するクラス | 正しく呼んだか（**振る舞いの検証**） |
| **ダミー** | 中身が空 | 引数を埋めるだけ。検証しない |

**核心**: スタブとモックの違いは「クラスの作りの違い」ではなく、**何を確かめたいかの違い**。

```
スタブ: テスト対象 ──呼ぶ──→ [固定値を返すニセモノ]
        確かめるのは「テスト対象の戻り値」      ← ニセモノは脇役

モック: テスト対象 ──呼ぶ──→ [呼ばれ方を記録するニセモノ]
        確かめるのは「ニセモノがどう呼ばれたか」 ← ニセモノが主役
```

**監査ログのように戻り値が `void` のものは、モックでしか検証できない**（戻り値が無いので状態の検証ができない）。これがモックが必要になる典型。

### 1-2. 実行結果（実測）

```
=== ① スタブ ===         OK  Q1〜Q4
=== ② フェイク ===       OK  Q5〜Q6
=== ③ モック ===         OK  Q7〜Q11
=== ④ 境界の組み合わせ === NG  Q12 （期待=22713, 実際=22712）
結果: OK 12件 / NG 1件
```

**Q12のNGは、仕込んだバグではない。** §3で扱う。

### 1-3. 「何ステップ通るか」を手で数える

```bash
java CoverageDrill.java
```

カバレッジ計測ツールがやっているのは、**通った行に印をつけて数えるだけ**。それを手で書いたのがこのファイル。

実測結果:

| テストケース | C0 命令網羅 | C1 分岐網羅 | C2 条件網羅 |
|---|---|---|---|
| A: `(70,true)` の1件だけ | **4/4 = 100%** | 1/2 = 50% | 2/4 = 50% |
| B: A + `(70,false)` | 4/4 = 100% | 2/2 = 100% | 3/4 = 75% |
| C: B + `(60,true)` | 4/4 = 100% | 2/2 = 100% | 4/4 = 100% |

**ここが一番大事**: ケースAは**全ステップ通っている（C0 100%）のに、ifのfalse側を一度も通っていない**。

> 「カバレッジ100%です」と報告されたら、**必ず「どのカバレッジですか」と聞く**。
> 公共系の案件では C0（命令網羅）と C1（分岐網羅）の両方に目標値があることが多い。

| 用語 | 何を数えるか | 日本の現場での呼び方 |
|---|---|---|
| C0 | 文（ステートメント）を通ったか | 命令網羅、ステートメントカバレッジ、**「何ステップ通ったか」** |
| C1 | if の true/false 両方を通ったか | 分岐網羅、ブランチカバレッジ |
| C2 | `&&`でつないだ個々の条件を両方通ったか | 条件網羅 |

**「ステップ」はソースの行数のこと**（公共系では規模をステップ数＝行数で数える文化がある）。「何ステップ通るか」＝ほぼC0の話。

| 分岐網羅（C1相当） | 5/8 = **62.5%** |
| 行 | 13/17 = **76%** |

### 2-4. Mockitoと手書きの対応

`TaxServiceTest.java` を読むと、Phase1で手書きしたものと1対1で対応している。

| 手書き（Phase1） | Mockito（Phase2） | 意味 |
|---|---|---|
| `new StubRepository(車両)` | `when(repository.findById("A-001")).thenReturn(車両)` | 値を返させる＝**スタブ化** |
| `MockAuditLog#callCount()` | `verify(auditLog).record("...")` | 呼ばれ方の検証＝**モック** |
| `MockAuditLog` の未呼び出し確認 | `verify(auditLog, never()).record("...")` | 呼ばれていないことの検証 |
| 手でnewして渡す | `@Mock` + `@InjectMocks` | ニセモノを作って組み立てる |

**`@Mock` で作ったものは、スタブにもモックにもなる。** `when` で値を返させればスタブ的な使い方、`verify` で呼ばれ方を見ればモック的な使い方。**道具は同じで、使い方（確かめたいこと）が違うだけ** ——ここが前の案件で混乱しやすいポイント。

### 2-5. 課題: 赤と黄を消す

`TaxServiceTest.java` の末尾にTODOが3つある。レポートの赤い行を見てから書く。

1. 13年以上の重課（`ageYears=15`）
2. 減免あり（`reduced=true`）
3. 車両が見つからない場合（`assertThrows` ＋ 監査ログの検証）

書いたら `mvn test` → レポートを開き直す。**実測で 命令60/60・分岐8/8 の100%になることを確認済み**。

<details><summary>解答（自分で書いてから開く）</summary>

```java
@Test
void 重課() {
    when(repository.findById("C-001")).thenReturn(new Vehicle("C-001", 1500, 15, false));
    assertEquals(45425, taxService.calculate("C-001"));
}

@Test
void 減免() {
    when(repository.findById("D-001")).thenReturn(new Vehicle("D-001", 1500, 3, true));
    assertEquals(19750, taxService.calculate("D-001"));
}

@Test
void 車両なし() {
    when(repository.findById("Z-999")).thenReturn(null);
    assertThrows(IllegalArgumentException.class, () -> taxService.calculate("Z-999"));
    verify(auditLog).record("車両なし:Z-999");
}
```

`assertThrows` と `verify` の import が要る:
```java
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.mockito.Mockito.verify;
```
</details>

## 3. 最大の落とし穴: カバレッジ100%でも見つからないバグ

ここが今日の本題。

### 3-1. Q12のNGは何だったのか

Phase1で唯一NGだった Q12（重課＋減免の組み合わせ）:

```
39,500円 → 重課15% → 45,425円 → 減免50% → 45,425 ÷ 2 = 22,712.5円
                                            実装は int 計算なので 22,712円（切り捨て）
```

**このNGは「実装のバグ」とも「テストの期待値が勝手な仮定」とも言い切れない。** なぜなら、**1円未満をどう扱うか（切り上げ／切り捨て／100円未満切り捨て）が仕様に書かれていない**から。

> これが実務で一番価値のある気づき方。
> **期待結果を書こうとして手が止まったら、それは仕様の穴。**
> → day2 §4 のQA表に「減免後の端数処理の扱い」として起票し、お客様に確認する。
> 自分で「たぶん切り捨てだろう」と決めてテストを書くのが一番やってはいけないこと。

### 3-2. そして、カバレッジ100%でもこれは見つからない

§2-5で命令100%・分岐100%を達成したが、**そのテスト一式にQ12（重課かつ減免）のケースは入っていない**。

```
重課テスト:  ageYears>=13 が true、reduced が false
減免テスト:  ageYears>=13 が false、reduced が true
                 ↓
         両方の if の true/false を通ったので 分岐網羅100%
                 ↓
         しかし「両方同時に true」の組み合わせは一度も通っていない
```

| | 重課なし | 重課あり |
|---|---|---|
| **減免なし** | テスト済 | テスト済 |
| **減免あり** | テスト済 | **未テスト ← 端数のバグはここに居る** |

> ### 結論
> **カバレッジは「足りていないことの証明」には使えるが、「十分であることの証明」には使えない。**
> 組み合わせの漏れ・境界値の誤り（`>=` を `>` と書き間違え）は、カバレッジ100%でも素通りする。
> だから [reading/03](reading/03-test-design.md) のデシジョンテーブル・境界値分析が別途必要になる。

### 3-3. 現場での使い方

| 言われたこと | どう受け取るか |
|---|---|
| 「C0カバレッジ80%が目標です」 | 下限の目安。達成しても品質の証明にはならない |
| 「カバレッジ100%なので品質OKです」 | **赤信号**。組み合わせ・境界値・異常系の観点が別途あるかを確認する |
| 「カバレッジが60%しかない」 | これは明確に問題。**通っていない行＝一度も動かしていないコード**が4割ある |

## 4. 改造課題（余力があれば）

1. **doubleをやめる**: `TaxService` の `(int)(tax * 1.15)` を整数演算（`tax * 115 / 100`）に直し、テストが通ることを確認する。
   - 実測事実: `(int)(39500 * 1.15)` はたまたま 45425 で一致するが、**x=1,300 では double計算が1,494、整数計算が1,495 と1円ずれる**（確認済み）。金額をdoubleで扱ってはいけない理由がこれ。
   - 本来は `BigDecimal` を使い、端数処理（`RoundingMode`）を明示する。
2. **端数処理を仕様として決める**: 「減免後は切り上げ」と仮に決めて実装し、Q12が通るようにする。決めた内容をコメントではなく**テストの名前**に書く（`減免後の端数は切り上げる()`）。
3. **組み合わせのテストを足す**: 重課×減免の4パターンを `@ParameterizedTest` で書く。
