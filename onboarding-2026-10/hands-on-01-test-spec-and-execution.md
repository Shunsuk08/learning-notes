# ハンズオン1: 試験仕様書の標準フォーマットと実際の試験実施

項目1（結合試験・総合試験推進）の深掘り。[day1 §1](day1-subleader-and-setup.md#1-結合試験総合試験推進) が「試験計画・バグの流れ」という管理者視点の話だったのに対し、ここは**手を動かして試験仕様書を書き、実際にテストする**ところまでをやる。

**前提**: [day1 午後A](day1-subleader-and-setup.md#a-環境構築とterasolunaの起動) で `~/git/terasoluna-todo/todo` が起動できる状態になっていること（まだなら先にそちらをやる）。

## これをやる理由

前職（運用保守）では、試験仕様を自分で自由な形式で書き、手元で動かして確認していた。今回の案件は**チームで試験仕様書を作り、第三者（レビュアー・お客様）が読める決まったフォーマットで残す**必要がある。フォーマットが決まっている理由は2つ。

1. **誰が書いても同じ粒度で読める**（自己流だと、書いた本人にしか分からない省略が起きる）
2. **「期待結果」を実施前に書く**ことで、結果を見てから基準を合わせる（後出しジャンケン）を防げる

---

## 1. 試験仕様書の一般的な構成

現場によって細部は違うが、SIer・受託開発ではだいたい次の2階層になっている。

| 階層 | 何を書くか | 読む人 |
|---|---|---|
| 試験項目書（大項目） | 機能一覧 × 試験する観点（[reading/03](reading/03-test-design.md#5-網羅を見える化する-観点表)の観点表そのもの） | リーダー・お客様が進捗と網羅性を確認する |
| テストケース一覧（詳細） | 1行＝1手順・1期待結果の具体ケース | 試験の実施者が1行ずつ上から実施する |

### テストケース一覧の標準列

| 列 | 書くタイミング | 内容 |
|---|---|---|
| No. | 作成時 | 例: `IT-結合-001`（IT=結合試験、ST=総合試験で接頭辞を分けると後で集計しやすい） |
| 大項目／中項目 | 作成時 | 機能名・画面名 |
| 前提条件 | 作成時 | この手順を始める前にデータ・状態がどうなっているべきか |
| 手順 | 作成時 | 操作を番号付きで。誰がやっても同じ操作になる粒度で書く |
| 入力データ | 作成時 | 具体的な値。「適当な値」は禁止（再現できなくなる） |
| **期待結果** | **作成時（実施前）** | 仕様から導く。「〜のはず」ではなく仕様書・設計書の該当箇所を根拠にする |
| 実施結果 | 実施時 | 実際に起きたこと（画面のコピー、ログの抜粋、HTTPステータス等の事実） |
| 判定 | 実施時 | 期待結果と実施結果が一致＝OK、不一致＝NG |
| 実施日／実施者 | 実施時 | 誰がいつやったかの記録（再現性・監査のため） |
| 不具合No. | NGのとき | バグ管理表の番号を紐づける（day1 §1の「バグの流れ」につながる） |

**やってはいけないこと**: 実施結果を先に（動かしてから）書いて、それに期待結果を合わせること。これをやると試験の意味がなくなる。

## 2. 練習1: 今あるHello Worldに対して試験仕様書を書く

Day1で起動した `http://localhost:8081/todo/` （Hello worldとサーバー時刻が出る画面）を対象に、**自分で**下の表を埋める。正解は1個ではないので、まず自分で書いてから見本と見比べる。

### 自分で書く表（埋めてみる）

| No. | 手順 | 入力データ | 期待結果 | 実施結果 | 判定 |
|---|---|---|---|---|---|
| IT-結合-001 | `/todo/` にアクセスする | なし | ？ | | |
| IT-結合-002 | 存在しないパス `/todo/abc` にアクセスする | なし | ？ | | |
| IT-結合-003 | `/todo/` にPOSTでアクセスする（画面はGETしか想定していない） | なし | ？ | | |

<details><summary>見本（埋めてから開く）</summary>

| No. | 手順 | 入力データ | 期待結果 | 実施結果（例） | 判定 |
|---|---|---|---|---|---|
| IT-結合-001 | `/todo/` にアクセスする | なし | HTTPステータス200。画面に「Hello world!」と現在時刻が表示される | ステータス200、本文に"Hello world!"と時刻を確認 | OK |
| IT-結合-002 | 存在しないパス `/todo/abc` にアクセスする | なし | HTTPステータス404（Tomcatの標準エラー画面） | ステータス404を確認 | OK |
| IT-結合-003 | `/todo/` にPOSTでアクセスする | なし | HTTPステータス405（Method Not Allowed）。Spring MVCは`@RequestMapping`でGETのみ許可している場合405を返す | 実際に確認すること（下記コマンド参照） | 実施して記入 |

</details>

### 実際に動かして「実施結果」を埋める

ブラウザではなく `curl` を使うと、ステータスコードや応答ヘッダーまで確認できて、試験の記録として残しやすい。

```bash
# IT-結合-001: 正常系
curl -i http://localhost:8081/todo/

# IT-結合-002: 存在しないパス
curl -i http://localhost:8081/todo/abc

# IT-結合-003: 許可されていないメソッド
curl -i -X POST http://localhost:8081/todo/
```

`-i` はレスポンスヘッダーを含めて表示するオプション。1行目の `HTTP/1.1 200` のような部分が「実施結果」の核。**IT-結合-003の結果は、実際にやってみるまで決め打ちしない**（200番台 or 405かはSpring MVCの設定次第。見本の「期待結果」は仕様からの推測であり、実施して違っていたらそれ自体が気づき）。

出力をそのままこのファイルの表の「実施結果」列にコピーして、OK/NGを自分で判定する。

## 3. 練習2: 自分で機能を1つ足して、試験仕様書を先に書く（テストファースト）

Hello Worldだけでは判定ロジックが無く、試験の練習としてはまだ物足りない。`HelloController` に**名前を受け取るパラメータ**を1つ足し、簡単な入力チェックを入れる。

### 作る機能（日本語フローパイプ）

```
1. クエリパラメータ name を受け取る
2. nameが未入力なら「ゲスト」として扱う
3. nameが20文字を超えていたら、画面に「名前は20文字以内で入力してください」とだけ表示する
4. それ以外は「{name}さん、こんにちは」とサーバー時刻を表示する
```

**ここが今回のポイント**: コードを書く前に、下の試験仕様書を先に埋める。期待結果が決まってから実装に入る（期待結果を決めるために、上の日本語フローパイプを仕様だと思って読む）。

| No. | 手順 | 入力データ（`?name=`） | 期待結果 | 実施結果 | 判定 |
|---|---|---|---|---|---|
| IT-結合-004 | 正常な名前でアクセス | `太郎` | | | |
| IT-結合-005 | パラメータを付けずにアクセス | （無し） | | | |
| IT-結合-006 | 境界値ちょうど（20文字） | 20文字の文字列 | | | |
| IT-結合-007 | 境界値超え（21文字） | 21文字の文字列 | | | |
| IT-結合-008 | 空文字を明示的に渡す | `name=`（空） | | | |
| IT-結合-009 | 危険な文字列（[reading/03](reading/03-test-design.md#a-入力値)のXSS観点） | `<script>alert(1)</script>` | | | |

期待結果の列は自分の言葉で埋める（4.の「日本語フローパイプ」から導けるはず）。IT-結合-009だけヒント：Spring MVCのJSPタグ（`<c:out>`やEL式の自動エスケープ）を使っていれば、スクリプトはそのまま実行されず文字列として表示される。**ここを確かめるのが、項目14（Spring Security基礎）のXSS対策の伏線**になる。

### 実装する

`HelloController.java` を開き、上の4行の日本語フローパイプどおりに実装する。分からないアノテーション（`@RequestParam`等）はSpring公式リファレンスかJavadocで調べる（AIに聞くのは行き詰まってから）。

実装できたら `mvn -DskipTests package` → warを差し替え → `curl` で6ケース全部を実施し、「実施結果」「判定」を埋める。

<details><summary>実装のヒント（詰まったら）</summary>

- `@RequestParam(required = false, defaultValue = "ゲスト") String name` で2.がほぼ片付く
- 文字数チェックは `name.length() > 20`
- JSP側でそのまま `${name}` と書けば、Spring（JSTL EL）はデフォルトでHTMLエスケープする。`<c:out value="${name}" escapeXml="false">` のように**わざと外さない限り**IT-結合-009はXSSされない。これが「デフォルトで安全」という設計の意味

</details>

## 4. 結合試験と総合試験の境目を、今の教材で確認する

| | 今できる範囲（Hello World／6ケース） | Day3以降でできる範囲 |
|---|---|---|
| 結合試験 | Controller単体の入力チェック・画面表示の確認 | Controller→Service→Mapper→実DB（Day3のMyBatis版Todoアプリ） |
| 総合試験 | まだできない（DB・現新比較・性能がないと総合試験とは言えない） | 現新比較（既存システムとの突き合わせ）、性能、可用性（[reading/03 §4](reading/03-test-design.md#4-非機能の網羅)） |

**このハンズオンは「結合試験のフォーマットと実施の体の動かし方」を身につけるのが目的で、本物の結合試験・総合試験の練習はDay3のMyBatis版Todoアプリに進んでから**。そこで同じフォーマット（上の表の列）をそのまま使い回せることを確認する。

## 確認問題

**Q1.** なぜ「期待結果」は実施前に書くのか。前職の「自由に書いて手元で確認」のやり方と比べて、何が変わるか。

<details><summary>答えの例</summary>

実施してから期待結果を書くと、起きた結果に基準を合わせてしまい、バグを見逃す（後出しジャンケン）。前職の自己流は、書いた本人の頭の中にしか判定基準が無かったが、先に書く方式では**第三者が後から見ても、何を根拠にOK/NGと判定したか**が分かる。レビュアーやお客様が試験仕様書だけを見て網羅性を判断できることも大きな違い。
</details>

**Q2.** IT-結合-007（21文字）のテストケースだけ書いて、IT-結合-006（20文字ちょうど）を書き忘れていた。何が問題か。

<details><summary>答え</summary>

[reading/03 §2-1](reading/03-test-design.md#2-1-同値分割と境界値分析) の境界値分析どおり、`>` と `>=` を書き間違えるバグは境界のすぐ両側で起きる。片側だけでは「20文字はOKで21文字はNGになる」のか「20文字から既にNGになっている」のかを区別できない。
</details>

**Q3.** IT-結合-009で、もし実際に `<script>` がそのまま実行されてしまった（＝JSP側で `escapeXml="false"` 等が設定されていた）場合、判定はOK/NGのどちらで、不具合として誰に・どう報告するか。

<details><summary>答えの例</summary>

NG。day1 §3の報告の型を使う：【事実】name=`<script>alert(1)</script>` で画面にアラートが実行された【影響】XSS脆弱性。公共案件ではセキュリティ不具合は重大度が高い【原因】（調査中、または該当JSPの記述を特定済みなら記載）【対策案】エスケープを有効にする【お願い】重大度の判断とお客様への報告要否をリーダーに確認。静的解析（項目5）で検出できる種類の不具合でもあるので、なぜ事前に拾えなかったかも5Why（項目6）の対象になる。
</details>
