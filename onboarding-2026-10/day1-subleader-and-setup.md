# 午前（座学）

## 0. サブリーダーの役割

**判断はリーダーがする。サブリーダーは判断材料をつくり、決まったことをチームで実行させる。**

前々案件（基幹システムの保守、30名規模）では、他チームの遅れを見つけてフォローしていた。これは「自分で気づいて自分で動く」だった。サブリーダーではこれが **「気づいて、整理して、リーダーに上げる。決まったら動かす」** に変わる。自分が手を動かす割合は下がり、見る範囲が広がる。

### 3本柱（毎日見るもの）

| 柱 | 見るもの | 毎日の問い |
|---|---|---|
| 進捗 | 予定と実績の差 | 「どこで止まっているか？」 |
| 課題 | 起きている問題・決まっていないこと | 「誰が・いつまでに・何を決めるか決まっているか？」 |
| 品質 | バグの数と傾向、レビュー指摘 | 「数字は想定どおりか？偏っていないか？」 |

### 5つの考え方

1. **判断はリーダー、判断材料は自分**: 事実を集め、選択肢と自分の推奨を添えて渡す。「どうしましょう？」だけで上げない。
2. **悪い報告ほど早く**: 遅れは「リカバリできるか・何が要るか」とセットで出す。ただし案ができるのを待って遅らせない。「事実だけ先に出し、対策は○時までに出す」でよい。
3. **感覚ではなく数字で話す**: 「ちょっと遅れてます」ではなく「予定10本のうち実績6本、残り4本、期限まで2日」。
4. **人ではなく状態を追う**: 「Aさんが遅い」ではなく「Aさんの担当機能はレビュー待ちで2日止まっている」。原因を人に置くと、本人が問題を隠すようになる。
5. **最初の2週間は変えずに観察する**: 既存の管理表・会議体・暗黙ルールが成り立っている理由を知る前に変えない。

## 1. 結合試験・総合試験推進

> 会社資料の教材: 『ソフトウェアテスト技法ドリル』『基礎から学ぶソフトウェアテスト』、JSTQB Foundationシラバス
> **書籍の代わり**: 下の要約 ＋ [JSTQB Foundation Level シラバス 日本語版（無料PDF）](https://jstqb.jp/dl/JSTQB-SyllabusFoundation_VersionV40.J02.pdf) の「テストレベル」「テストの管理」の章だけ

### 試験の種類（何を確かめるか）

| 試験 | 確かめること | 主な担い手 |
|---|---|---|
| 単体試験（UT） | 1つのクラス・メソッドが設計どおり動くか | 開発者 |
| 結合試験（IT） | 機能同士・画面とDB・外部システムがつながって動くか | 開発チーム |
| 総合試験（ST） | システム全体が業務として使えるか。性能・障害時の動きも見る | 開発チーム＋お客様 |

更改案件では、**現行システムと同じ結果になるか（現新比較）** が試験の大きな柱になることが多い。

### 試験計画書に書かれていること（参画したら最初に読む）

| 項目 | 見るポイント |
|---|---|
| 範囲 | どの機能・どの外部連携が対象か。対象外は何か |
| 開始条件 | UTが終わっていること、環境・データが揃っていること等 |
| **終了条件** | 「全ケース消化」「重大バグ0件」「バグ曲線が収束」など。**サブリーダーが一番意識する** |
| 体制・スケジュール | 誰がどの機能を何日で |
| 環境・データ | 試験環境が何面あるか、他チームと共有か |
| 品質目標 | テスト密度・バグ密度の目標値（下の項目2） |

### バグ（欠陥）の流れ

```
起票 → 分析（原因・影響範囲） → 修正 → 再試験 → 確認 → 完了
                                              ↘ 差し戻し（直っていない）
```

サブリーダーが見るのは、**どこで止まっているバグが多いか**。「分析待ちが多い＝調査できる人が足りない」「再試験待ちが多い＝試験担当が足りない」と、止まっている場所で打ち手が変わる。

### バグ曲線（信頼度成長曲線）

- 横軸＝消化ケース数（または工数）、縦軸＝累積バグ件数
- **曲線が寝てくる（新しいバグが出にくくなる）＝収束**
- 落とし穴: 横軸を日付にすると、テストしなかった日も曲線が寝て、収束したように見える
- 件数だけでなく**重要度別**にも見る。後半に重大バグが出ているなら終わってはいけない

## 2. 品質管理の基本

> 会社資料の教材: 『PMBOKガイド』『SQuBOK』
> **書籍の代わり**: 下の要約 ＋ [IPA ソフトウェア開発 分析データ集 2022（無料PDF）](https://www.ipa.go.jp/digital/software-survey/metrics/hjuojm000000c6it-att/000102171.pdf) の「テスト密度」「不具合密度」の章だけ眺める

### 品質は「作り込む」と「見つける」の2つ

- **作り込む**: 設計レビュー・コードレビュー・コーディング規約・静的解析
- **見つける**: 試験

後ろの工程で見つかるバグほど直すコストが高い。だから品質管理では、**レビューで見つけた件数**と**試験で見つけた件数**の両方を見る。

### 指標

| 指標 | 計算 | 何が分かるか |
|---|---|---|
| テスト密度 | テストケース数 ÷ 規模（KLOC、画面数など） | テストが足りているか |
| バグ密度（欠陥密度） | バグ件数 ÷ 規模 | 作りの品質。低すぎても高すぎても要注意 |
| レビュー指摘密度 | 指摘件数 ÷ ページ数（またはKLOC） | レビューが機能しているか |
| テスト消化率 | 消化済みケース ÷ 予定ケース | 進捗 |
| 未解決バグ数 | 起票済み − 完了 | 修正が追いついているか |

### ゾーン分析（テスト密度 × バグ密度）

| | バグ密度 低 | バグ密度 高 |
|---|---|---|
| **テスト密度 高** | 良好の可能性が高い | 作りが悪い。前工程（設計・UT）を疑う |
| **テスト密度 低** | **一番危ない**。テスト不足でバグを見つけられていないだけかもしれない | テストを増やせばもっと出る |

**基準値は案件の品質計画書にある。** 参画したら最初に探す。基準を外れたら「外れた理由の分析」をリーダーに出すのが仕事。

## 3. 進捗管理・課題管理

> 会社資料の教材: 『マンガでわかるプロジェクトマネジメント』『PMBOKガイド』、IPAプロジェクトマネージャ試験教材
> **書籍の代わり**: 下の要約 ＋ Web記事（中身はClaude側で未確認。自分で読み、食い違いをメモする）
> - [システム開発マネジメントの基本（PMの役割・WBS・PERT等）— Sun*](https://sun-asterisk.com/service/development/topics/systemdev/4822/)
> - [サブチームリーダーの役割とは？— ONES](https://ones.com/ja/blog/sub-team-leader-role-skills/)

### 進捗: WBSと予実

- **WBS**: 成果物を作業単位に分解した一覧。1行が「誰が・何を・いつからいつまで」。
- **予実**: 予定と実績の比較。進捗管理とは予実の差を毎日見ること。

「80%です」という申告は当てにならない（**90%症候群**: 90%まではすぐ行くが、残り10%が終わらない）。対策は **完了の基準を成果物で決めること**。

| 数え方 | 例 | 特徴 |
|---|---|---|
| 自己申告％ | 「80%くらいです」 | 楽だが楽観に寄る |
| 0/100 | 完了したら100、それ以外は0 | 厳しいが確実 |
| 0/50/100 | 着手で50、完了で100 | 粒度が揃っていれば実用的 |
| 成果物ベース | テストケース120件中85件消化 | 結合試験ではこれが基本 |

**遅れの兆候**: 同じタスクが3日以上「作業中」／質問が急に減った／「あと少しです」が2回続いた／想定外の調査タスクが増えた／修正の差し戻しが増えた

### 課題とリスクの違い

| | 課題（Issue） | リスク（Risk） |
|---|---|---|
| 時制 | **もう起きている** | **まだ起きていない** |
| 例 | 試験環境のDBが壊れて試験が止まっている | 来週、試験環境を他チームと取り合う可能性がある |
| やること | 対応する（誰が・いつまでに） | 確率と影響を見積もり、予防策と発生時の対策を決めておく |

**リスクは放っておくと課題になる。** サブリーダーの価値は、リスクの段階で拾ってリーダーに見せること。

### 課題票の書き方

| 項目 | コツ |
|---|---|
| 件名 | 「何が・どうなっている」が一行で分かる。「DBの件」は不可 |
| 内容 | **事実だけ**。推測は「見立て」欄に分ける |
| 影響 | どの作業・どの期限に効くか |
| 対応者 | **名前は1人だけ**（複数だと誰もやらない） |
| 期限 | 「いつまでに何が決まるか」 |
| 完了条件 | 何をもって閉じるか |

### リーダーに上げる基準

案件で決まった基準があればそれに従う。無いときは次のどれかに当たれば上げる。迷ったら上げる。

1. **期限**: マイルストーンに効く遅れが出る、または出そう
2. **お客様**: お客様の判断・確認が必要
3. **範囲**: 自チームの外（他チーム・インフラ・別ベンダー）の協力が要る
4. **品質**: 同じ種類のバグが続く、重大なバグが出た
5. **人**: メンバーの体調・負荷・人間関係

### 報告の型（そのまま使う）

```
【事実】結合試験 機能Bは予定40件に対し実績25件（-15件）
【影響】このままだと10/20の完了予定が2日遅れる見込み
【原因】試験環境のデータ準備で1.5日止まった（解消済み）
【対策案】①Cさんが10/14〜15に応援 ②優先度の低い10件を後ろ倒し
【お願い】どちらで進めるか今日中に判断をお願いしたい（推奨は①）
```

## A. 環境構築とTERASOLUNAの起動

公式チュートリアル（5.11.0.RELEASE）: <https://terasolunaorg.github.io/guideline/current/ja/Tutorial/TutorialTodo.html>

公式はWindowsとSTS（Eclipse）が前提。ここではMacのターミナルで同じことをする手順にしている。**10/1にClaudeがこのMacで試し、手順4で「Hello world!」が出ることを確認済み。**

### 手順1: ツールを入れる

```bash
brew install maven
mvn -v   # Maven 3.9.x と Java の版数が出ればOK
```

- **Mavenを選ぶ理由**: TERASOLUNAのブランクプロジェクトはMaven前提（archetypeで生成する）。
- **代替**: SDKMANでMavenとJDKをまとめて管理する方法もあり、複数のJDKを切り替えるなら便利。
- **JDK**: 手元はJDK 25。ブランクのpomは `<java-version>17</java-version>` で、JDK 25でビルド・起動できることは確認済み。案件がJava 17ならJDK 17も入れておくと差が出ない（`brew install --cask temurin@17`）。必須ではない。

### 手順2: ブランクプロジェクトを作る

公式の `^` はWindowsの改行記号。Macでは `\` にする。

```bash
mkdir -p ~/git/terasoluna-todo && cd ~/git/terasoluna-todo
mvn archetype:generate -B \
 -DarchetypeGroupId=org.terasoluna.gfw.blank \
 -DarchetypeArtifactId=terasoluna-gfw-web-blank-jsp-archetype \
 -DarchetypeVersion=5.11.0.RELEASE \
 -DgroupId=com.example.todo \
 -DartifactId=todo \
 -Dversion=1.0.0-SNAPSHOT
cd todo && git init && git add . && git commit -m "chore: ブランクプロジェクト生成"
```

最初にコミットしておくと、後で `git diff` を見るだけで「自分が何を書いたか」をレビューできる。

### 手順3: ビルドする

```bash
mvn -DskipTests package
ls -la target/todo.war   # 約30MBのwarができる
```

### 手順4: Tomcat 11で起動する

pomにサーバ起動用のプラグインは入っていない。WARをTomcatに置いて起動する。

```bash
mkdir -p ~/tools && cd ~/tools
curl -LO https://archive.apache.org/dist/tomcat/tomcat-11/v11.0.15/bin/apache-tomcat-11.0.15.tar.gz
tar xzf apache-tomcat-11.0.15.tar.gz
```

**8080番はstudymate-aiのバックエンドが使っていることがある**（`lsof -iTCP:8080 -sTCP:LISTEN` で確認できる）。Tomcat側を8081に変える。

```bash
cd ~/tools/apache-tomcat-11.0.15
sed -i '' 's/port="8080"/port="8081"/; s/port="8005"/port="8015"/' conf/server.xml
cp ~/git/terasoluna-todo/todo/target/todo.war webapps/
bin/startup.sh
tail -f logs/catalina.out   # 「Server startup in」が出たらCtrl+C
```

ブラウザで <http://localhost:8081/todo/> を開き、「Hello world!」とサーバ時刻が出れば成功。止めるときは `bin/shutdown.sh`。

- 起動しないとき: `logs/catalina.*.log` を `grep -i "重大\|SEVERE"` で絞ってから読む（AIにログを丸ごと貼らない練習にもなる）。
- コードを直したら `mvn -DskipTests package` → warをコピー → Tomcatが自動で再デプロイする。

### 手順6: 読んで図にする

コード読解の型どおり、**入口から呼ばれる順に読む**。今回の入口は `main` ではなく `web.xml`。

1. `src/main/webapp/WEB-INF/web.xml` を開き、`listener-class` と `filter-class` を書き出す

読んだら、**次の図を紙かdraw.ioに描く**。

- 箱: `app`（Controller）／`domain`（Service・Repository・Model）／`infra`
- 矢印: どの層がどの層を呼ぶか（依存の向き）

## 確認問題

**Q1.** リーダーから「機能Cの結合試験、どう？」と聞かれた。テスト消化は予定30件・実績18件。担当者は「明日には追いつきます」と言っている。報告の型で返せ。

<details><summary>答えの例</summary>

「予定30件に対し実績18件で-12件です。担当は明日挽回できると言っていますが、1日の消化ペースは平均6件なので、明日だけで12件は難しいと見ています。明日の夕方時点で24件を下回っていたら、応援か後ろ倒しを相談させてください」。本人の申告をそのまま流さず、**ペース（数字）で裏を取り、判断のタイミングを先に決めておく**。
</details>

**Q2.** 次を課題とリスクに分け、リスクなら予防策を1つ書け。(a) 試験環境が明日から3日間、他チームの性能試験で使えないと連絡があった (b) メンバーのBさんが来月から別案件に移る噂がある (c) 機能Dの設計書と実装で、エラーメッセージの文言が違う

<details><summary>答えの例</summary>

(a) 課題（もう決まっている）。試験の順番を入れ替える、別環境を借りる。(b) リスク（噂の段階）。リーダーに事実確認を依頼し、Bさん担当分の引き継ぎ資料を早めに作ってもらう。(c) 課題。どちらが正しいかをお客様・設計者に確認する必要がある＝上げる基準の「お客様」に当たる。
</details>

**Q3.** バグ曲線がここ3日ほぼ横ばいになり、メンバーが「収束しました」と言っている。確認すべきことを2つ挙げよ。

①その3日間、テストを予定どおり消化していたか（横軸が日付だと、テストしていないだけでも横ばいになる）。②後半に出たバグの重要度。他に、残りのテストケースが難しいケースばかりでないかも見る。

**Q4.** studymate-ai（Spring Boot）では `main` → `SpringApplication.run()` が起点だった。TERASOLUNAのブランクには `main` が無い。何が起点になってSpringが起動しているか。

<details><summary>答え</summary>

TomcatがWARを読み込み、`web.xml` に書かれた `ContextLoaderListener`（業務側のApplicationContext）と `DispatcherServlet`（Web側のApplicationContext）を起動する。**Spring Bootは「Tomcatを内蔵してmainから起動する」、従来型は「外のTomcatがSpringを起動する」**で、主従が逆。公共系の更改案件では従来型が多い。
</details>
