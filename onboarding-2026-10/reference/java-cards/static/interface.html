インターフェースと抽象クラス

「契約」と「実装」を分ける、Spring/DIの土台になる考え方
1インターフェース
「何ができるか」だけを定義する契約。実装は持たない（default/staticメソッドは例外）。
interface TaxRepository { void save(Vehicle v, int amount); }
2抽象クラス
共通の実装を持ちつつ、一部を子クラスに任せる。「です」の関係（IS-A）が強い場合に使う。
abstract class Vehicle { abstract int calculateTax(); String getPlateNo() { return plateNo; } // 共通実装 }
3なぜインターフェースに依存するか
実装クラスではなくインターフェースに依存させることで、実装を差し替えやすくなる（SOLIDのD）。テストでモックに差し替えるのも同じ理屈。
4Springでの実例
コンストラクタはインターフェース型で受け取り、実際の実装（クラス）はSpringがDIコンテナから注入する。
public TaxService(TaxRepository repo) { this.taxRepository = repo; // 実装はSpringが決める }
💡「型はインターフェース、中身は実装クラス」。コードを読むときは、どの実装が実際に注入されているかをセットで追う。
