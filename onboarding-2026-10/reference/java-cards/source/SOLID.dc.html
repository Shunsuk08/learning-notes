SOLID って？

保守しやすい設計の5原則
S
単一責任
1つのクラスの変更理由は1つだけにする。見通しが良くなる。
O
開放閉鎖
拡張には開き、修正には閉じる。追加しやすい設計にする。
L
置換原則
親クラスの代わりに子クラスを使っても壊れない。安全に入れ替えられる。
I
分離原則
インターフェースを小さく分ける。使わないメソッドへの依存を強制しない。
D
依存逆転
具体的な実装ではなく抽象（インターフェース）に依存する。差し替えやすくなる。
D（依存逆転）の実例：TaxServiceとDI
public TaxService(TaxRepository taxRepository) { // 抽象（インターフェース）に依存 this.taxRepository = taxRepository; // 実装はSpringが注入する }
💡レビューで指摘に結びつけやすいのはS（クラスが太りすぎ）とD（newで実装に直結）。まずこの2つから見る。
