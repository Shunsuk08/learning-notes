## 16. ソースコードレビュー観点

> 会社資料の教材: 『リーダブルコード』『Effective Java 第3版』『Clean Code』
> **書籍の代わり**: 下の要約。Day1午後の基本文法ドリルと、午後のレビュー演習がそのまま実践になる

### 固定チェックリスト（毎回この順に見る）

| # | 観点 | 典型例 |
|---|---|---|
| 1 | null | 戻り値・引数・DBの任意項目をそのまま使っている。`Optional#get()` を確認なしで呼んでいる |
| 2 | 境界値 | `<=` と `<` の取り違え、0件・1件・上限ちょうど |
| 3 | 型・比較 | 文字列やラッパー型（`Integer`）を `==` で比べている、お金を `double` で計算している |
| 4 | 例外 | 握りつぶし、`catch (Exception e)`、原因の例外を捨てている |
| 5 | リソース | ファイル・接続を閉じていない（try-with-resources を使う） |
| 6 | トランザクション | `private` メソッドや自分のクラス内呼び出しに `@Transactional`、検査例外でコミットされる |
| 7 | セキュリティ | `${}` によるSQL組み立て、エスケープ漏れ、**個人情報をログに出している** |
| 8 | 重複・可読性 | 同じ処理のコピペ、意味の分からない名前、長すぎるメソッド |

### Effective Java から押さえる5つ（書籍の代わり）

1. `equals` を書いたら `hashCode` も書く（Day1ドリルQ5）
2. 変更されないオブジェクト（不変）を優先する
3. 例外は「例外的な状況」にだけ使う。制御の流れに使わない
4. `null` を返す代わりに空のコレクションや `Optional` を返す
5. 正確な計算（お金）には `float` / `double` を使わず `BigDecimal` を使う（Day1ドリルQ3）

### テストケースの作り方

| 技法 | 考え方 | 未完了の上限5件のチェックなら |
|---|---|---|
| 同値分割 | 同じ動きをする入力のまとまりごとに1つ選ぶ | 「上限未満」「上限以上」から1つずつ |
| 境界値分析 | まとまりの境目を狙う（バグは境目に集まる） | 未完了が **4件（作れる）／5件（作れない）** |

### テストの形（AAA）

```java
@Test
void 未完了が5件のときは作成できない() {
    // Arrange（準備）: Repositoryが「未完了5件」と答えるようにする
    // Act（実行）: create を呼ぶ
    // Assert（確認）: BusinessException が投げられる
}
```

- テストメソッド名は日本語で「条件と期待結果」を書いてよい（案件の規約を確認する）
- **DBなどの外側はモック（Mockito）に置き換え**、Serviceの業務ロジックだけを試す

## 21. DR基礎

> 会社資料の教材: AWS Well-Architected Framework Reliability Pillar、IPA事業継続ガイドライン
> - [AWS Well-Architected 信頼性の柱（日本語）](https://docs.aws.amazon.com/ja_jp/wellarchitected/latest/reliability-pillar/welcome.html)（災害対策の章だけ）

| 用語 | 意味 | 覚え方 |
|---|---|---|
| RPO（目標復旧時点） | **どの時点のデータまで戻せればよいか** | データをどれだけ失ってよいか（過去の方向） |
| RTO（目標復旧時間） | **どれだけの時間で復旧すればよいか** | どれだけ止まってよいか（未来の方向） |

RPO・RTOを短くするほどコストが上がる。**業務の重要度から決めるもの**で、技術から決めるものではない。

## 22. AWSでのDRアーキテクチャ

> 会社資料の教材: AWS Disaster Recovery Whitepaper、AWS Solutions Library、AWS SAP/SAA認定教材
> - [AWS 上のワークロードのディザスタリカバリ（ホワイトペーパー、日本語）](https://docs.aws.amazon.com/ja_jp/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-workloads-on-aws.html)

### DRの4つの戦略（下ほどRTO/RPOが短く、コストが高い）

| 戦略 | 平常時の待機側 | 復旧の速さ |
|---|---|---|
| バックアップと復元 | バックアップだけ | 数時間〜 |
| パイロットライト | DBなど核の部分だけ常時複製、サーバは止めておく | 数十分〜 |
| ウォームスタンバイ | 縮小した構成で常時稼働 | 数分〜 |
| マルチサイト（アクティブ/アクティブ） | 両方で本番を処理 | ほぼ即時 |

### マルチAZとマルチリージョン

- **マルチAZ**: 同じリージョン内の別データセンター群。1つのデータセンターの障害に備える（可用性）
- **マルチリージョン**: 東京と大阪のように地理的に離す。広域災害に備える（DR）

前案件のECS on Fargate構成を思い出し、「あの構成でRPO・RTOを決めるなら何を足すか」を1つ考えてみる（例: RDSのリージョン間レプリカ、S3のリージョン間レプリケーション、Route 53のフェイルオーバー）。

## B. JUnitでTodoServiceの単体テストを書く（60分）

ブランクプロジェクトにはJUnit 5とMockitoが最初から入っている（10/1にpom.xmlで確認済み）。Day3で作った `todo-mybatis3` に書く。

1. `src/test/java/com/example/todo/domain/service/todo/TodoServiceImplTest.java` を作る
2. 先に**テストケースの一覧を日本語で書く**（同値分割・境界値）。最低でも次の4つ:
   - 未完了が4件のとき、作成できる
   - 未完了が5件のとき、`BusinessException`
   - 未完了のTodoを完了にできる
   - 完了済みのTodoを完了にしようとすると `BusinessException`
3. テストを書いて `mvn test` で通す

雛形（Repositoryのメソッド名は自分のコードに合わせる）:

```java
@ExtendWith(MockitoExtension.class)
class TodoServiceImplTest {

    @Mock
    TodoRepository todoRepository;

    @InjectMocks
    TodoServiceImpl todoService;

    @Test
    void 未完了が5件のときは作成できない() {
        // Arrange: 未完了件数を数えるメソッドが 5 を返すように when(...).thenReturn(5L)
        // Act & Assert: assertThrows(BusinessException.class, () -> todoService.create(todo));
    }
}
```

**わざとServiceのバグを入れて（上限の判定を `>` と `>=` で入れ替える等）、テストが落ちることも確かめる**。落ちないテストは役に立たない。
