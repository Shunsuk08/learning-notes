# テスト結果の分析と、テスト用語集

[day1 §2（品質管理の基本）](../day1-subleader-and-setup.md#2-品質管理の基本)で指標の種類とゾーン分析の考え方を扱った。ここはその先の **「数字が出たあと、どう読んで、どう説明するか」** と、**会議で飛び交う用語の辞書**。

> **出典の確度**: 以下の基準値は、IPA『ソフトウェア開発分析データ集』を解説した**記事経由**で得た数値（原典PDFは未確認）。**会議で使うなら必ず原典か案件の品質計画書を確認する。** 案件に品質計画書があれば、そこの基準値が常に優先。

---

## 1. 数字の相場観（IPAデータ集・記事経由）

「この数字は多いのか少ないのか」を判断するための物差し。KSLOC＝ソースコード1,000行。

| 指標 | 工程 | 中央値 | 妥当とされる範囲 |
|---|---|---|---|
| テスト密度（件/KSLOC） | 結合テスト | 約37.6 | 約20〜80 |
| テスト密度（件/KSLOC） | 総合テスト | 約9.4 | 約5〜20 |
| 不具合密度（件/KSLOC） | 結合テスト | 約1.11 | 約0.65〜2.61 |
| 不具合密度（件/KSLOC） | 総合テスト | 約0.20 | 約0.09〜0.83 |
| ケースあたり不具合検出率 | 結合テスト | — | 約2〜5% |

**読み方の例**: 結合テストで1,000行あたり40件のテストをして、バグが1件出る、くらいが「普通」。100件テストして3件前後バグが出る。

**注意**: 規模をKSLOCで測るのは、画面数・機能数で測る案件もあり一律ではない。**更改案件では流用部分をどう数えるか**で密度が大きく変わるので、分母の定義を必ず確認する。

## 2. 数字が基準から外れたときの読み方

[day1 §2のゾーン分析](../day1-subleader-and-setup.md#ゾーン分析テスト密度--バグ密度)に、数値と「次の一手」を足したもの。

```
                 バグ密度 低い                     バグ密度 高い
              ┌──────────────────────┬──────────────────────┐
  テスト密度  │ ① 良好の可能性        │ ② 作り込み品質が悪い  │
  高い        │ ただし「ケースが     │ 前工程(設計・UT)を    │
              │ 甘い」可能性も疑う   │ 疑う。レビュー強化    │
              ├──────────────────────┼──────────────────────┤
  テスト密度  │ ③ 一番危ない         │ ④ テスト不足かつ      │
  低い        │ テスト不足でバグを   │ 品質も悪い            │
              │ 見つけられていない   │ テスト追加で更に出る  │
              └──────────────────────┴──────────────────────┘
```

**サブリーダーの仕事は、外れたこと自体ではなく「外れた理由の説明」を作ること。** 説明の候補を先に持っておく。

| 外れ方 | ありえる理由（これを調べる） |
|---|---|
| テスト密度が低い | 流用部分が多い／ケースの粒度が粗い／観点が漏れている／規模の数え方が違う |
| テスト密度が高い | ケースを細かく割りすぎ／同じ観点の重複／自動生成で水増し |
| バグ密度が低い | 作りが良い／**テストが甘い**／バグを起票せずその場で直している（←要注意） |
| バグ密度が高い | 設計の品質が悪い／仕様変更が多い／新規参画メンバーが多い／難易度の高い機能 |

**「バグを起票せずにその場で直す」は数字を壊す**。品質が良く見えてしまい、傾向分析もできなくなる。チームに最初に徹底することの1つ。

## 3. バグ曲線（信頼度成長曲線）の読み方

横軸＝消化ケース数（または工数）、縦軸＝累積バグ件数。収束＝曲線が寝てくること。ゴンペルツ曲線・ロジスティック曲線というS字カーブで近似することが多い。

```
  累積バグ件数
    │                      ③頭打ち（理想的な収束）
    │                 ┌────────────
    │              ／
    │           ／     ②立ち上がり（バグが一気に出る時期）
    │        ／
    │   ___／           ①初期（環境不備等で進まない時期）
    └─────────────────────────── 消化ケース数
```

### 危険なパターン

```
  【発散型】まだ出続ける              【直線型】収束判断できない
    │        ／                        │      ／
    │      ／                          │    ／
    │    ／                            │  ／
    │  ／                              │／
    └────────                          └────────
  テスト継続が必要。終了条件を満たさない   テストが単調／観点が偏っている疑い

  【階段型】                          【早すぎる収束】
    │    ┌──┐                         │ ┌──────────
    │ ┌──┘                            │ │
    │ │                               │ │
    └────────                          └────────
  特定機能でまとめて出ている           テストが甘い／難しいケースが未消化
  → 機能別の傾向分析へ                  → 消化率と中身を確認
```

### 収束と判断する前に確認する3点

1. **横軸は消化ケース数か**（日付にすると、テストしなかった日も寝て見える＝day1 §1の落とし穴）
2. **重大度別でも寝ているか**（後半に重大バグが出ているなら収束ではない）
3. **残りのケースは何か**（難しいケース・異常系だけ残っていないか）

## 4. 傾向分析（どこに偏っているか）

件数の合計だけ見ても打ち手は出ない。**切り口を変えて偏りを探す**のが分析の本体。

| 切り口 | 見えること | 打ち手の例 |
|---|---|---|
| **機能別** | 特定機能にバグが集中 | その機能の設計レビューをやり直す／テストを追加 |
| **原因分類別** | 仕様誤解か、実装ミスか、設計漏れか | 仕様誤解が多い→仕様の伝え方／設計漏れ→レビュー観点 |
| **検出工程 × 作り込み工程** | **流出分析**。どの工程で作られ、どの工程で見つかったか | 設計のバグが結合で見つかる＝レビューが機能していない |
| **ステータス別** | 分析待ち・修正待ち・再試験待ちのどこで滞留しているか | 滞留箇所に人を割り当てる（day1 §1のバグの流れ） |
| 時系列 | 増え方の変化 | 急増したタイミングで何が起きたか（新機能投入・環境変更） |

### 流出分析の表（公共系でよく求められる）

| 作り込み工程＼検出工程 | UT | 結合 | 総合 | 本番（流出） |
|---|---|---|---|---|
| 要件定義 | — | 2 | 5 | 0 |
| 基本設計 | 1 | 8 | 3 | 0 |
| 詳細設計 | 12 | 6 | 1 | 0 |
| 実装 | 45 | 9 | 0 | 0 |

**右上（前工程で作られ、後工程で見つかった）が多いほど、前工程のレビューが効いていない。** 左下は正常（作った直後に見つかっている）。

### 人を責めない使い方

担当者別の集計は**出し方を間違えると逆効果**（バグを隠す、起票しなくなる）。使うなら「特定の人に負荷や難しい機能が偏っていないか」を見るためで、評価の材料にしない。day1 §0の「人ではなく状態を追う」と同じ。

## 5. 品質会議での説明の型

数字を読み上げるだけの報告は価値が低い。**「事実 → 解釈 → 打ち手」**の順に組む。

```
【事実】結合テスト 機能Bのバグ密度は2.8件/KSLOC（基準上限2.6を超過）
【解釈】原因分類では「仕様誤解」が6件中4件。他機能では1割程度なので、
        機能B固有の問題と見ている
【背景】機能Bは仕様変更が3回入っており、変更が実装者まで伝わっていなかった
【打ち手】①機能Bの変更分だけ設計レビューを再実施（10/8まで）
        ②変更連絡の経路を課題票として起票済み（#124）
【判断してほしいこと】①の工数2人日を確保してよいか
```

**ポイント**: 基準を外れたことを隠さない・言い訳しない。**外れた理由の仮説と、確かめ方をセットで出す。**

## 6. テスト用語集

会議・仕様書で飛び交う用語。**似ているが別物**のものを隣に並べている。

### 6-1. テストダブル（本物の代わりに使うニセモノ）

```
   【スタブ】テスト対象が「呼び出す側」の代わり      【ドライバ】テスト対象を「呼び出す」代わり

   ■テスト対象 ──呼ぶ──→ □スタブ                □ドライバ ──呼ぶ──→ ■テスト対象
   （決まった値を返してくれる）                    （上位モジュールが未完成なときに使う）
```

| 用語 | 意味 | 使いどころ |
|---|---|---|
| **スタブ** | テスト対象から**呼ばれる側**の代替。決まった値を返す | 下位モジュール・外部システムが未完成 |
| **ドライバ** | テスト対象を**呼び出す側**の代替 | 上位モジュール（画面など）が未完成 |
| **モック** | 呼ばれ方（回数・引数）を**記録して検証**する代替 | 「正しく呼んだか」を確かめたいとき |
| **スパイ** | 本物を呼びつつ、呼ばれ方も記録する | 本物の動作を保ちながら確認したいとき |
| **フェイク** | 簡易だが**実際に動く**実装（インメモリDB等） | day2のTodoアプリのMap実装がこれ |
| **ダミー** | 引数を埋めるためだけ。実際には使われない | 必須引数を埋めるとき |
| テストハーネス | テストを動かすための仕掛け一式（ドライバ＋スタブ＋実行環境） | — |
| フィクスチャ | テストの前提データ・前提状態 | 「テストデータ」とほぼ同義で使われる |

**覚え方**: スタブは**下**（呼ばれる側）、ドライバは**上**（呼ぶ側）。モックは「結果」ではなく「**やりとり**」を見る。

### 6-2. テストレベル・種類

| 用語 | 意味 |
|---|---|
| UT / 単体テスト | 部品1つを確かめる（[05](05-test-levels-boundary.md)） |
| ITa / 内部結合 | サブシステム内部のつなぎ |
| ITb / 外部結合 | サブシステム間・外部システムとのつなぎ |
| ST / 総合テスト | システム全体で要件を満たすか |
| UAT / 受入テスト | お客様が業務として使えるか確かめる |
| 回帰テスト（リグレッション） | 修正により**既存機能が壊れていないか**の再確認。工程ではなく目的 |
| 確認テスト（再テスト） | バグ修正が**正しく直ったか**の確認。回帰テストとは別物 |
| スモークテスト | 最低限動くかの素早い確認。工程の入口で行う |
| 現新比較 | 現行と新システムに同じ入力を与え、出力が一致するか確かめる。更改案件の要 |
| ホワイトボックステスト | 内部のコード構造を見て作るテスト |
| ブラックボックステスト | 仕様だけを見て、内部を知らずに作るテスト |

### 6-3. 技法・網羅

| 用語 | 意味 |
|---|---|
| 同値分割 | 同じ動きをする入力のまとまりに分け、代表値で試す |
| 境界値分析 | まとまりの境目の両側を試す（[03 §2-1](03-test-design.md#2-1-同値分割と境界値分析)） |
| デシジョンテーブル | 条件の組み合わせと結果を表にする |
| 状態遷移テスト | 状態×操作の表を作り、ありえない遷移も試す |
| ペアワイズ | どの2条件の組み合わせも1回は試す、に絞る方法 |
| エラー推測 | 経験から壊れやすい箇所を狙う |
| カバレッジ（C0/C1/C2） | コードのどれだけを通ったか。C0＝命令網羅、C1＝分岐網羅、C2＝条件網羅 |
| 観点表 | 機能×観点のマトリクス。空白が漏れ（[03 §5](03-test-design.md#5-網羅を見える化する-観点表)） |
| トレーサビリティ | 要件→観点→ケースがたどれる状態 |

### 6-4. 指標・分析

| 用語 | 意味 |
|---|---|
| テスト密度 | テストケース数 ÷ 規模 |
| バグ密度／不具合密度 | バグ件数 ÷ 規模 |
| レビュー指摘密度 | 指摘件数 ÷ ページ数（またはKLOC） |
| 消化率 | 消化済みケース ÷ 予定ケース |
| 検出率 | バグ件数 ÷ 実施ケース数 |
| 未解決バグ／滞留バグ | 起票済みで完了していないバグ |
| 流出不具合 | 後工程・本番で見つかった、前工程で防げたはずのバグ |
| 信頼度成長曲線／バグ曲線／PB曲線 | 累積バグ件数の推移グラフ |
| ゴンペルツ曲線 | バグ曲線の近似に使うS字カーブ（非対称） |
| 収束 | 新しいバグが出にくくなり、曲線が寝た状態 |
| ゾーン分析 | テスト密度×バグ密度の4象限で品質を判断 |

### 6-5. 運用・プロセス

| 用語 | 意味 |
|---|---|
| 試験項目書 | 機能×観点の大項目一覧 |
| テストケース一覧 | 1行＝1手順・1期待結果の詳細 |
| エビデンス（証跡） | 実施した証拠（画面キャプチャ・ログ） |
| 起票 | バグ・課題を管理表に登録すること |
| 差し戻し | 修正が不十分でテスト担当に戻ってくること |
| 棚卸し | 残課題・残バグを一覧で確認し直すこと |
| 終了条件（完了基準） | 試験を終わってよい条件（全ケース消化・重大バグ0・曲線収束など） |
| Go/NoGo判定 | 次の工程・本番移行に進んでよいかの判断 |
| QA表 | お客様への確認事項一覧（day2 §4） |

### 6-6. 自動化

| 用語 | 意味 |
|---|---|
| テストピラミッド | 単体を厚く、E2Eを薄くする自動テストの配分モデル |
| E2Eテスト | 画面から通して端から端まで確認する自動テスト |
| フレイキーテスト | 同じコードなのに成功したり失敗したりする不安定なテスト |
| オートヒーリング | UI変更でテストが壊れたとき、AIが自動修復する機能 |
| Testcontainers | テスト時に本物のDB等をDockerで起動するライブラリ |
| CI | コードをpushするたびに自動でビルド・テストする仕組み |

## 7. 確認問題

**Q1.** 結合テストで、機能Aのバグ密度が0.2件/KSLOC（基準下限0.65を下回る）だった。「品質が良い」と報告してよいか。

<details><summary>答え</summary>

まだ言えない。ゾーン分析の③（テスト密度が低いと最も危ない）を確認する。テスト密度も低いなら「テスト不足でバグを見つけられていないだけ」の可能性が高い。あわせて、バグを起票せずその場で直していないか、観点が漏れていないか（観点表の空白）を確認する。**密度が基準を外れたときは、良い方向でも理由の説明が要る。**
</details>

**Q2.** スタブとドライバの違いを、1行ずつで説明せよ。

<details><summary>答え</summary>

スタブ＝テスト対象が**呼び出す側**（下位モジュール・外部システム）の代わりで、決まった値を返す。ドライバ＝テスト対象を**呼び出す側**（上位モジュール）の代わりで、テスト対象を動かす。
</details>

**Q3.** 「バグ曲線が収束したので結合テストを終了したい」とメンバーが言ってきた。確認する3点は。

<details><summary>答え</summary>

①横軸が消化ケース数か（日付だとテストしていない日も寝る）②重大度別でも寝ているか（後半に重大バグが出ていないか）③残っているケースは何か（難しいケース・異常系だけ残っていないか）。加えて、案件の終了条件（全ケース消化・未解決バグ件数）を満たしているかを計画書で確認する。
</details>

**Q4.** 流出分析の表で「基本設計で作り込まれ、総合テストで検出されたバグ」が増えている。これは何を意味するか。

<details><summary>答え</summary>

基本設計のレビューと、結合テストの両方をすり抜けているということ。設計レビューの観点不足（day4 §15）と、結合テストの観点不足（03の観点表の空白）の両方を疑う。後工程で見つかるほど修正コストが高いので、**今後の機能についてレビュー強化を提案する材料**になる。
</details>
