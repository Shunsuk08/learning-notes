# テスト設計の読み物: 観点の出し方と、異常系・非機能の網羅

day1 §1（結合試験・総合試験推進）と §2（品質管理）の深掘り。単体・結合テストを実施した経験はある前提で、**「どうやってテストケースを漏れなく出すか」**に絞る。

## この読み物のゴール

1. テストケースを「思いつき」ではなく、**観点（切り口）から機械的に**出せるようになる
2. **異常系**を、カテゴリ別のチェックリストで漏れなく出せるようになる
3. **非機能**（性能・可用性・セキュリティなど）で何を確かめるかが分かる
4. サブリーダーとして、**他人の試験仕様書の漏れ**を指摘できるようになる

---

## 1. テスト設計の考え方

### テストは「動くこと」ではなく「壊れ方」を探す作業

正常系（言われたとおりに使ったら動く）は、作った本人も確かめている。バグが隠れているのは、**作った人が想定しなかった使われ方**の方。

| 種類 | 何を確かめるか | 漏れやすさ |
|---|---|---|
| 正常系 | 仕様どおりの入力・操作で、期待どおり動くか | 低い |
| 準正常系 | 想定内の誤り（未入力、桁超え、権限なし）を、正しく弾くか | 中くらい |
| 異常系 | 想定外の事態（DB停止、タイムアウト、二重実行）でも、壊れないか | **高い** |

「準正常系」と「異常系」を分けて呼ぶ現場もあれば、まとめて「異常系」と呼ぶ現場もある。現場の呼び方に合わせる。

### テストケースは「観点 → 条件 → ケース」の順に作る

いきなりケースを書くと、思いついたものしか出ない。

```
観点（何を確かめるか） 例: 金額の入力チェック
  ↓
条件（どんな値・状態で） 例: 0円、上限ちょうど、上限＋1、マイナス、未入力、文字
  ↓
ケース（手順と期待結果） 例: 金額に「-1」を入力して登録 → 「金額は0以上で入力してください」が出る。DBは更新されない
```

**サブリーダーがレビューで見るのは「観点」の段階。** ケースの書き方より、観点が足りているかの方が重要。

### 期待結果は「画面」だけでなく「データ」と「ログ」まで

異常系で特に大事。エラーメッセージが出ても、裏でデータが半分だけ更新されていたら不具合。

| 確かめる場所 | 例 |
|---|---|
| 画面 | エラーメッセージの文言、遷移先、入力値が残っているか |
| データ | **更新されていないこと**（ロールバック）、件数が変わっていないこと |
| ログ | エラーが記録されているか、**個人情報が出ていないか** |
| 外部 | 外部システムに中途半端なデータを送っていないか |

## 2. テスト技法（観点からケースを出す道具）

### 2-1. 同値分割と境界値分析

入力値を「同じ動きをするまとまり」に分け、まとまりの**境目**を狙う。バグは境目に集まる（`<` と `<=` の書き間違いなど）。

例: 「金額は1円以上、999,999円以下」

| まとまり | 代表値 | 境界値 |
|---|---|---|
| 小さすぎる（エラー） | -100 | **0** |
| 正しい | 50,000 | **1**、**999,999** |
| 大きすぎる（エラー） | 5,000,000 | **1,000,000** |

境界値は、**境目の両側**（0と1、999,999と1,000,000）を必ずセットで試す。

### 2-2. デシジョンテーブル（条件の組み合わせ）

条件が複数あり、組み合わせで結果が変わるときに使う。

例: 「減免の対象か」の判定（説明用に簡略化した架空のルール）

| 条件 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 障害者手帳あり | ○ | ○ | × | × |
| 本人または同一世帯の所有 | ○ | × | ○ | × |
| **結果: 減免対象** | **○** | × | × | × |

条件が3つなら 2 × 2 × 2 ＝ 8列。**全組み合わせを表にすると、仕様書に書かれていない組み合わせが見つかる**（「この組み合わせのときはどうなる？」を確認する材料になる）。

### 2-3. 状態遷移テスト

データに「状態」があり、操作で状態が変わる機能に使う。Todoの「未完了 → 完了」や、申請の「下書き → 申請中 → 承認 → 取消」など。

```
[下書き] --申請--> [申請中] --承認--> [承認済]
                      |
                      +--差戻し--> [下書き]
[承認済] --取消--> [取消済]
```

確かめるのは2種類。

1. **正しい遷移**: 矢印のとおりに変わるか
2. **ありえない遷移**: 矢印が無い操作をしたら弾かれるか ← **漏れやすい**
   - 承認済みのものをもう一度「申請」する
   - 取消済みのものを「承認」する
   - Todoの完了済みをもう一度「完了」にする（day2 改造課題3）

状態 × 操作の表を作ると、ありえない遷移が全部出る。

| 状態＼操作 | 申請 | 承認 | 差戻し | 取消 |
|---|---|---|---|---|
| 下書き | 申請中へ | **弾く** | **弾く** | **弾く** |
| 申請中 | **弾く** | 承認済へ | 下書きへ | **弾く** |
| 承認済 | **弾く** | **弾く** | **弾く** | 取消済へ |
| 取消済 | **弾く** | **弾く** | **弾く** | **弾く** |

「弾く」のマスが、異常系のテストケースになる。この例では12マス。

### 2-4. 組み合わせテスト（ペアワイズ）

条件が多すぎて全組み合わせが試せないとき、**「どの2つの条件の組み合わせも、少なくとも1回は試す」**ように絞る方法。不具合の多くは2つの条件の組み合わせで起きる、という経験則に基づく。

例: ブラウザ3種 × 利用者の種別3種 × 支払い方法4種 ＝ 36通り → ペアワイズなら12通り前後に絞れる（専用ツールで作る）。

### 2-5. エラー推測

経験から「ここは壊れやすい」と推測して試す。次の章のチェックリストは、エラー推測を誰でもできるようにまとめたもの。

## 3. 異常系の網羅チェックリスト

**ここがこの読み物の本題。** 機能ごとに、次のカテゴリを上から当てていく。全部が当てはまるわけではないので、当てはまらないものは「対象外」と書いて飛ばす（**飛ばした理由を残すと、レビューで漏れと区別できる**）。

### A. 入力値

| 観点 | 試す値の例 |
|---|---|
| 未入力 | 空、スペースだけ、改行だけ |
| 桁・長さ | 最大桁ちょうど、最大桁＋1、0桁 |
| 型 | 数字欄に文字、小数、全角数字「１２３」 |
| 範囲 | 境界値（2-1） |
| 文字種 | 全角／半角、カナの全角半角、記号 `< > ' " & ;` |
| **外字・旧字体** | 「髙」「﨑」「𠮷」など。**公共系では氏名・住所で頻出**。文字化け・桁数の数え方（1文字が2〜4バイト）を確認 |
| 前後の空白 | 「 山田」「山田 」→ 検索で一致するか |
| 日付 | 2月29日（うるう年とそうでない年）、2月30日、月末、**和暦の境目**（平成31年4月30日／令和元年5月1日） |
| 危険な文字列 | `<script>`（XSS）、`' OR '1'='1`（SQLインジェクション） |

### B. 業務の状態

| 観点 | 例 |
|---|---|
| 二重登録 | 同じデータを2回登録しようとする |
| ありえない状態遷移 | 完了済みを完了、取消済みを更新（2-3の表） |
| 存在しないデータ | URLのIDを書き換えて、存在しないIDを開く |
| 削除済みデータ | 一覧を開いたまま、別の画面で削除してから操作する |
| 期限・期間 | 受付期間の前日・初日・最終日・翌日 |
| **権限** | 権限の無いユーザーで操作する。**URLを直接打って、他人のデータを見られないか** |

### C. 画面の操作

| 観点 | 例 |
|---|---|
| 二重送信 | 登録ボタンを素早く2回押す |
| ブラウザの戻る | 登録完了画面で「戻る」→ もう一度登録 |
| 再読み込み | 登録完了画面でF5（day3 §11 のPRGパターン） |
| 複数タブ | 同じデータを2つのタブで開いて、両方で更新 |
| セッション切れ | 30分放置してから登録ボタンを押す |

### D. 同時実行（排他）

| 観点 | 例 |
|---|---|
| 同時更新 | AさんとBさんが同じデータを同時に開き、Aさんが更新 → Bさんが更新 |
| 期待結果 | Bさんの更新が**エラーになる**（楽観ロック）か、**待たされる**（悲観ロック）か。**Aさんの更新が黙って上書きされていたら不具合** |
| 上限チェックの割り込み | 「未完了5件まで」のチェック直後に、別の人が登録する（day2 確認問題Q3） |

### E. データの量と中身

| 観点 | 例 |
|---|---|
| 0件 | 一覧が0件のとき、エラーにならず「該当なし」が出るか |
| 1件・上限ちょうど | ページングの境目（1ページ20件なら、20件と21件） |
| 大量 | 本番相当の件数で、一覧・検索・帳票が時間内に終わるか（→ 非機能の性能） |
| null・空 | 任意項目が未登録のデータ（day2 §6 の例: 所有者が未登録） |
| 関連データの欠け | 親データはあるが、子データが無い |

### F. 外部連携

| 観点 | 例 |
|---|---|
| 相手が止まっている | 接続できない |
| タイムアウト | 相手が応答しない（**何秒で諦めるか**が設計されているか） |
| 不正な応答 | 想定外の形式、項目欠け、文字コード違い |
| 部分的な失敗 | 100件送って、50件目で失敗 → **どこまで送れたか分かるか、再送で重複しないか** |
| 再送 | 同じデータを2回受け取ったとき、二重に登録されないか |

### G. バッチ（夜間の一括処理）

| 観点 | 例 |
|---|---|
| 入力ファイル | 無い、空、壊れている、想定より大きい |
| 途中で止まった | 50%で強制停止 → **再実行して正しく終わるか**（最初からやり直しか、続きからか） |
| 二重起動 | 同じバッチを2つ同時に起動する |
| 日付の境目 | 0時をまたぐ、月末・年度末、**祝日・年末年始**（業務日の計算） |
| 処理時間 | 本番相当の件数で、決められた時間内に終わるか |

### H. 環境・インフラ

| 観点 | 例 |
|---|---|
| DB | 処理中にDB接続が切れる |
| ディスク | 一時ファイル・ログの出力先がいっぱい |
| 再起動 | APサーバを再起動しても、処理中のデータが壊れていないか |

## 4. 非機能の網羅

非機能は「どう動くか」ではなく「**どれくらいの品質で動くか**」。主に**総合試験**で確かめる。公共系では、IPAの**非機能要求グレード**の6つの大項目を下敷きにしていることが多い。

- [IPA 非機能要求グレード](https://www.ipa.go.jp/archive/digital/iot-en-ci/jyouryuu/hikinou/ent03-b.html)（項目一覧だけ眺める）

| 大項目 | 何を確かめるか |
|---|---|
| 可用性 | 止まらないか、止まってもすぐ戻るか |
| 性能・拡張性 | 速いか、利用者やデータが増えても耐えるか |
| 運用・保守性 | 監視・バックアップ・障害対応がやりやすいか |
| 移行性 | 現行システムから正しく移せるか |
| セキュリティ | 不正に使われないか、情報が漏れないか |
| システム環境・エコロジー | 動作環境（OS・ブラウザ等）、設置条件 |

### 4-1. 性能

| 種類 | 確かめること | 例 |
|---|---|---|
| 応答時間 | 1回の操作が何秒で返るか | 画面表示3秒以内 |
| スループット | 単位時間あたり何件処理できるか | 1時間あたり1万件の登録 |
| 同時アクセス | 何人が同時に使っても応答時間を守れるか | 300人同時 |
| バッチ処理時間 | 夜間の決められた時間内に終わるか | 22時〜翌6時の間 |
| 長時間稼働 | 何日も動かし続けて遅くならないか、メモリが増え続けないか | 72時間連続 |
| **ピーク** | 一番混む時期の量で耐えるか | **納期限の直前、年度初め、月末** |

性能試験で大事なのは、**本番と同じデータ量**で試すこと。開発環境の100件では速くても、本番の500万件では遅いことがよくある。

### 4-2. 可用性

| 確かめること | 例 |
|---|---|
| 冗長化の切り替え | 2台構成の1台を止めたとき、もう1台に切り替わるか。**切り替わる間に処理中だったデータはどうなるか** |
| 再起動からの復旧 | サーバを再起動して、決められた時間内に業務を再開できるか |
| バックアップと復元 | バックアップから実際に**戻せるか**（取るだけでなく、戻す試験をする） |

day4 §21 のRPO・RTOが、ここの合格基準になる。

### 4-3. 運用・保守性

| 確かめること | 例 |
|---|---|
| 監視 | エラーが起きたら、監視ツールにアラートが上がるか |
| ログ | 障害調査に必要な情報（日時・ID・処理名）が出ているか。**個人情報が出ていないか** |
| 運用手順 | 手順書どおりに、バッチの再実行・データの修正ができるか |

### 4-4. セキュリティ

| 確かめること | 例 |
|---|---|
| 認証 | パスワード誤りを繰り返したらロックされるか |
| 認可 | 権限外の機能・他人のデータに、URL直打ちでアクセスできないか |
| セッション | ログアウト後に「戻る」で画面が見えないか、タイムアウトするか |
| 入力値 | XSS・SQLインジェクション（3-A） |
| 脆弱性診断 | 専門のツール・業者による診断が計画されているか |

### 4-5. 移行性

| 確かめること | 例 |
|---|---|
| 件数 | 現行と新システムで、データ件数が一致するか |
| 金額 | 金額の合計が一致するか |
| 現新比較 | 同じ入力で、現行と新システムの出力（画面・帳票）が一致するか |

### 4-6. 互換性（システム環境）

| 確かめること | 例 |
|---|---|
| ブラウザ | 対象ブラウザ（Edge、Chromeなど）と版数で動くか |
| 画面サイズ | 想定する解像度で表示が崩れないか |

## 5. 網羅を「見える化」する: 観点表

機能 × 観点 のマトリクスを作り、試すマスに○、対象外に「－（理由）」を付ける。**空白のマスが漏れ**。

| 機能 | 入力値 | 状態 | 画面操作 | 排他 | 外部連携 | 性能 |
|---|---|---|---|---|---|---|
| 納付登録 | ○ | ○ | ○ | ○ | ○ | ○ |
| 納付照会 | ○ | ○ | ○ | －（参照のみ） | － | ○ |
| 夜間集計バッチ | ○（ファイル） | ○ | －（画面なし） | ○（二重起動） | ○ | ○ |

サブリーダーとして試験仕様書をレビューするときは、まずこの表を作り、**空白のマスを質問する**。「納付照会の性能は、どこで試験していますか？」

### トレーサビリティ

要件 → 観点 → テストケース が、たどれるようにしておく。「要件No.15を確かめているケースはどれか」に答えられないと、漏れが分からない。

## 6. よくある漏れ（アンチパターン）

| 漏れ | なぜ起きるか |
|---|---|
| 正常系ばかりで、異常系が1〜2件 | 仕様書に「正しい動き」しか書かれていない |
| 期待結果が「エラーになること」だけ | どのメッセージか、データが戻っているかが書かれていない |
| 境界値の片側しか試していない | 「上限ちょうど」だけで、「上限＋1」が無い |
| ありえない状態遷移が無い | 状態遷移図を描いていない |
| 開発環境のデータ量で性能を見ている | 本番のデータ量を確認していない |
| バックアップを取るだけで、戻していない | 「取れた」で満足している |
| 権限の試験が「画面にボタンが出ない」だけ | URLを直接打つ試験をしていない |

## 7. 確認問題

**Q1.** 次の画面の異常系テストケースを、3章のチェックリストを使って**15個以上**書き出せ。

> **納付登録画面**: 車両番号・納付日・納付金額を入力し、「登録」ボタンで登録する。登録すると、車両の状態が「未納」から「納付済」になる。納付金額は、その車両の税額と一致しなければならない。

<details><summary>答えの例（カテゴリ別）</summary>

**A. 入力値**
1. 車両番号が未入力
2. 車両番号が最大桁＋1
3. 車両番号に記号・`<script>`
4. 納付日が未入力
5. 納付日が存在しない日付（2月30日）
6. 納付日が未来日
7. 納付金額が0円・マイナス
8. 納付金額に文字・小数・全角数字
9. 納付金額が税額と1円違う（境界値）

**B. 業務の状態**
10. 存在しない車両番号
11. 既に「納付済」の車両に登録（ありえない状態遷移）
12. 廃車などで対象外の車両
13. 権限の無いユーザーで登録

**C. 画面の操作**
14. 登録ボタンの二重クリック → 2重に納付登録されない
15. 登録完了画面で「戻る」→ 再登録
16. セッション切れの後に登録

**D. 同時実行**
17. 2人が同じ車両を同時に納付登録 → 片方はエラー

**H. 環境**
18. 登録処理中にDB接続が切れる → 納付データだけ登録されて、車両の状態が「未納」のまま、にならないこと（ロールバック）

18個。**どれも期待結果に「DBが更新されていないこと」を含める**のがポイント。
</details>

**Q2.** 「一覧画面の表示が3秒以内」という要件がある。開発環境（データ100件）で0.5秒だった。性能の試験は合格と言えるか。

<details><summary>答え</summary>

言えない。本番のデータ量（例えば500万件）、同時アクセス数（ピーク時に何人か）、ピークの時期（納期限前）の条件で試す必要がある。「どの条件で試したか」を試験結果に必ず書く。
</details>

**Q3.** メンバーの試験仕様書をレビューしたら、「権限チェック: 一般ユーザーでログインすると、管理メニューが表示されないこと」の1件だけだった。何を指摘するか。

<details><summary>答え</summary>

画面にメニューが出ないことと、機能が使えないことは別。**管理機能のURLを一般ユーザーで直接開いて、拒否されること**を追加する。あわせて、他人のデータのIDをURLに入れて開けないこと（3-B）も確認する。
</details>
