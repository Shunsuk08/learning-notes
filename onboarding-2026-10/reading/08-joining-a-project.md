# 08 新しい案件に入った最初の数週間（体験記事の調査と、初日の聞くことメモ）

2026-10-04 調査。新しい現場に途中参画した人の体験記事を読み、「最初の1〜4週間で実際に何が起きたか」を集めた。本文まで読めたのは9本なので、件数は傾向として扱う。

## 1. 参画初期に起きること

| 項目 | 何が起きるか | 9本中 |
|---|---|---|
| 質問・報告の仕方 | 詰まって黙るのが一番の失敗。「〜と理解しましたが合っていますか」と言い直して確かめる。時間がかかりそうなら先に伝える | 4 |
| 人と役割の把握 | 顧客の担当者、関係会社、質問相手、緊急連絡先、挨拶すべき部署 | 4 |
| 記録して共有する | 口頭で聞いたルール、環境構築の手順、エラー対処、日報をメモし、次に来る人の資料にする | 4 |
| 焦らない・小さな約束を守る | 初日は情報が多すぎて頭に入らない。「明日見ます」を守ることで信頼が積み上がる | 4 |
| 手続き・現場ルール | 勤怠、貸与物（PC・入館証）、出入口、紛失時の連絡先 | 3 |
| 定例と報告の型 | 定例の日程、顧客に出す成果物、週報、自社への報告 | 3 |
| 環境構築 | 初日の午後か初週。手順を書き残すまでがセット | 2 |
| 用語の認識ズレ | 同じ言葉が前の職場と違う意味。略語が多く会議についていけない | 2 |
| 更改・公共に特有のこと | 設計書が更新されておらず実態と違う。紙の会議資料が大量、顧客の立場が強い、保守性が最優先 | 2 |

## 2. 自分の仮説との差分

事前の仮説は「環境構築・チームのドキュメント・勉強会」だった。

- 環境構築は記事にも出てくる。ただし「手順を書き残す」までがセット
- 勉強会を初期の主な活動として挙げた記事は、読んだ範囲では無かった
- 仮説に無かったもの：①人と連絡経路の把握 ②質問・報告の型 ③メモをチームの資料にする ④用語の認識合わせ ⑤設計書と実態のずれ（コード・実環境と照らし合わせる）

## 3. 初日〜初週に聞くことメモ（現場でチェックする）

### 手続き・ルール
- [ ] 勤怠の付け方、始業・終業、休憩
- [ ] 貸与物（PC・入館証）と、紛失時の連絡先
- [ ] 緊急連絡先（現場の上長・自社の営業）
- [ ] 持ち出し・撮影・私物PC/スマホのルール
- [ ] **Copilot に業務コードを渡してよい範囲**、使えるモデルと予算
- [ ] ネットワーク制限（外部サイト・パッケージ取得ができるか）

### 人と役割
- [ ] 顧客の担当者、関係会社、チームメンバーの名前と役割（図にする）
- [ ] 自分の質問相手は誰か。仕様・技術・進捗で相手が違うか
- [ ] サブリーダーとして、何を自分で決めてよく、何をリーダーに上げるか

### 会議と報告
- [ ] 定例の日程と参加者
- [ ] 日報・週報の形式と提出先（現場と自社の両方）
- [ ] 顧客に出す成果物と、その締め切り

### 技術・ドキュメント
- [ ] Java の版数、IDE、ビルドツール、DB、構成管理（Git か）
- [ ] TERASOLUNA の版数と、ブランクからの独自の改造があるか
- [ ] 設計書の置き場所、最終更新日、実態とずれている箇所はあるか
- [ ] 環境構築手順書はあるか（無ければ自分で書き残す）
- [ ] テストの単位（単体/結合/総合）の呼び方と、仕様書の形式
- [ ] 用語集はあるか（無ければ自分用に作り始める）

## 4. 自分用のテンプレート

**質問するとき**
> 〇〇まで分かりました。××が分かりません。△△と理解しましたが合っていますか。（調べた時間：◯分）

**30秒の自己紹介**
> 経歴（何年・何を）／得意分野／この案件でサブリーダーとして何をするか、の3文

**日報**：Day1 §3 の報告の型（結論→事実→課題→次の行動）を流用する
