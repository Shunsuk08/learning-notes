## 1. フォーマットの現実: 公共系・SIerはいまもExcel + エビデンス

### なぜExcelなのか

2026年でも、公共系・大手SIerの試験仕様書はExcel（またはスプレッドシート）が主流。理由は技術的な優位性ではなく**契約と検収**にある。

| 理由 | 中身 |
|---|---|
| 成果物として納品する | 試験仕様書・試験結果報告書が契約上の納品物。紙・PDFで提出・押印・保管する前提 |
| 第三者が検証できる | お客様・監査が、ツールのアカウント無しで中身を見られる必要がある |
| エビデンス（証跡）を貼る | 「実際にやった証拠」をスクリーンショットで残す文化。Excelは画像を貼れる |
| 全員が使える | 発注元・協力会社まで含めて、追加ライセンス無しで開ける |

**改善提案をするときに効く視点**: 「Excelが古いから変えましょう」は通らない。変えるなら「検収で求められる形（PDF・証跡）を出せること」をセットで示す必要がある。

### エビデンス（証跡）の残し方

| 項目 | 現場の標準的なルール |
|---|---|
| 何を残すか | 画面キャプチャ、ログの該当行、DBの更新前後、コマンドの実行結果 |
| ファイル名 | `機能名_ケース番号_日付.png` のように規則を決める（例: `納付登録_IT-001_20261005.png`） |
| 保存先 | 共有フォルダ／SharePointの決められた場所。**個人PCに置かない** |
| 貼り方 | Excelのセルに貼る、または「証跡の格納先パス」を列に書く（ファイルが重くなるため後者も多い） |
| 日時 | キャプチャに日時が写るようにする（画面の時計、ログのタイムスタンプ） |

**2026年の論点**: スクリーンショットだけでは不十分という議論が出ている（加工できる、文脈が残らない、AI生成画像と区別がつかない）。ログ・DBダンプ・自動テストの実行結果など、**改ざんしにくい記録とセットで残す**方向。参画後に案件のルールを確認する。

### 列の設計

標準列は [hands-on-01 §1](../hands-on-01-test-spec-and-execution.md#1-試験仕様書の一般的な構成) にある。実務ではこれに加えて次の列が付くことが多い。

| 追加列 | 用途 |
|---|---|
| 試験区分 | UT / ITa / ITb / ST（[05-test-levels-boundary](05-test-levels-boundary.md)） |
| 要件ID・設計書ID | トレーサビリティ（この要件を確かめているのはどのケースか） |
| 優先度 | 時間が足りないときに削る順番を事前に決めておく |
| 証跡ファイル名 | 上記のエビデンス |
| 再試験日・再試験判定 | バグ修正後の再確認（1回目の判定を消さずに残す） |

## 2. Excel以外の選択肢（知識として）

案件で使えるとは限らないが、**「他にどういうやり方があるか」を知っていること自体が、サブリーダーの引き出し**になる。

| ツール | 特徴 | 位置づけ |
|---|---|---|
| **TestRail** | 世界的な定番。国内はテクマトリックスが販売・サポート。Jira/Jenkins連携 | 国内実績・サポート重視ならこれ |
| **CAT** | SHIFT提供の国産。**Excel/スプレッドシート風UI**で移行しやすい | Excel文化からの移行先として相性が良い |
| **Qase** | モダンUI・API。AIアシスタント「AIDEN」搭載。自動テスト結果の取り込みに強い。無料枠あり | 小さく試すなら |
| **PractiTest** | 90か国以上で利用。日本語サポートあり | 大規模・多拠点向け |
| **Markdown + Git** | テストケースをMarkdownで書き、GitHubでレビュー・CIで実行（トレタの移行事例） | 開発者が書く・自動テストと一体化する場合 |

**共通して解決される課題**: バージョン管理、同時編集、進捗の自動集計、自動テスト結果の取り込み。
**共通して残る課題**: 納品物としての体裁、オフライン閲覧、お客様側のアカウント。

## 3. 自動テスト: どこを自動化するか

### テストピラミッド／トロフィー／ダイヤモンド

自動テストを「どの層に厚く置くか」のモデル。**2026年の実態は「アーキテクチャによって使い分ける」**で、ピラミッドが唯一の正解ではなくなっている（記事経由）。

```
     ピラミッド（モノリス向け）        トロフィー（SPA/フロント向け）     ダイヤモンド（マイクロサービス向け）

          /\  E2E 10%                    ▁▁  E2E 10%                       /\   E2E
         /  \                           ███████ 結合 60%                  /    \
        /----\ 統合 20%                  ███ 単体 20%                    ████████ 結合（厚い）
       /      \                          ▔▔▔ 静的解析（土台）             \      /
      /--------\ 単体 70%                                                  \    /  単体
```

| モデル | 向いている構成 | 考え方 |
|---|---|---|
| ピラミッド | モノリス（今回の案件に近い） | 速くて安い単体テストを厚く、遅くて壊れやすいE2Eは薄く |
| トロフィー | SPA・フロントエンド | 「結合テストが一番費用対効果が高い」という主張 |
| ダイヤモンド | マイクロサービス | サービス間の結合が本番の壊れどころなので、そこを厚く |

**覚えること**: 比率そのものより、**「E2E（画面を通した自動テスト）は壊れやすく遅いので、増やしすぎると回らなくなる」**という力学。手動E2Eを全部自動化しようとして破綻するのが典型的な失敗。

### Java / Spring の具体的な道具

| 道具 | 何をテストするか | レベル |
|---|---|---|
| JUnit 5 + Mockito | クラス単体。依存はモックで差し替え | 単体 |
| `@WebMvcTest` | Controller層だけ起動（Service以降はモック） | 単体〜結合の境目 |
| `@DataJpaTest` / Mapperテスト | DBアクセス層だけ。インメモリDBまたはTestcontainers | 結合（DB込み） |
| **Testcontainers** | **本物のPostgreSQL等をDockerで起動**してテスト | 結合 |
| `@SpringBootTest` | アプリ全体を起動して、Controller→Service→Repositoryを通す | 結合 |
| Selenium / Playwright | ブラウザを操作して画面から通す | E2E（総合試験寄り） |

**2026年のトレンド**: Testcontainersで**本番と同じDB製品**を使うのが標準化してきている（インメモリDBだとSQLの方言差でバグを見逃すため）。Spring Boot 3.1以降は `@ServiceConnection` で接続設定の記述が不要になった（記事経由）。

> **今回の案件での注意（未確認・要確認）**: TERASOLUNA 5.x は **Spring Boot ではなく素のSpring Framework + 外部Tomcat** 構成。`@SpringBootTest` はそのままでは使えず、`spring-test` の `@ContextConfiguration` / `@WebAppConfiguration` を使う形になる。**案件のテストの書き方は参画後に既存コードで確認する**（この段落はClaudeの一般知識からの推測であり、案件の実装は未確認）。

### 公共系・更改案件で自動テストが効くところ

結合試験フェーズから入る今回のような案件では、ゼロから自動テストを整えるのは現実的でない。効くのは次。

| 場面 | なぜ効くか |
|---|---|
| **現新比較** | 現行システムと新システムに同じ入力を流し、出力の差分を機械的に比較する。手作業だと件数を増やせない |
| **回帰テスト（リグレッション）** | バグ修正のたびに「前に動いていたところが壊れていないか」を確認する。手動だと毎回フルは回せない |
| **データ移行の検算** | 件数・金額合計の突き合わせはスクリプトが圧倒的に速い |

## 4. AI活用: 2026年の実態

### テスト設計（ケースを考える）側

生成AIでテストケースを作る取り組みは実用段階に入っている。ただし**丸投げでは使えない**というのが共通見解。

**効く使い方（記事で共通している「分解」のやり方）**:

```
① 機能抽出      仕様書から機能の一覧を出させる        ← 人がレビュー
② 観点抽出      各機能のテスト観点を出させる          ← 人がレビュー（ここが一番重要）
③ テスト条件    観点ごとの条件（境界値・状態）を出す   ← 人がレビュー
④ ケース生成    手順と期待結果の形に展開させる        ← 人がレビュー
```

一気に「テストケースを作って」と頼むと、**正常系に偏り、粒度がバラバラになる**。段階に分け、各段で人がレビューするのが定石。[03-test-design](03-test-design.md) の観点チェックリストを**AIに渡すプロンプトの材料**にすると、網羅の抜けが減る。

**向いていること / 向いていないこと**

| 向いている | 向いていない |
|---|---|
| 観点の洗い出しの「たたき台」 | 業務ルールの正しさの判断（仕様書にない暗黙ルールを知らない） |
| 同値分割・境界値の機械的な展開 | 案件固有の過去バグ・現場の勘所 |
| 書き方の統一（フォーマット整形） | 「何をテストしないか」の判断 |
| テストデータの大量生成 | お客様との合意が要る範囲の決定 |

### テストコード生成側

- GitHub Copilot / ChatGPT で単体テストを生成する実践は一般化。**既存コードに対するテストの初稿**としては実用的
- ある検証記事では、同じ課題でChatGPT-4oが一発動作、Copilotが修正1回、Claude 3.7 Sonnetが修正5回という結果（**1記事の限定的な実験であり、モデル・時期で変わる。この数字を一般論として引用しない**）
- **落とし穴**: AIが生成したテストは「今のコードの動き」をそのまま期待結果にしがち。**バグごと固定してしまう**（バグがあるコードに対して「バグった結果が返ること」をテストにしてしまう）。期待結果は必ず仕様から人が決める

### E2E自動化のAIツール（国内でよく出る3つ）

| ツール | 特徴 |
|---|---|
| **Autify** | 国産。ブラウザ操作の記録でテスト作成、画面変更に自動追従。AIエージェント「Autify Nexus」で自然言語指示、「Genesis」でテスト計画・設計の標準化 |
| **MagicPod** | 国産。ノーコードで高度な操作（HTTPリクエスト、二段階認証突破等）。**UI変更時にAIが自動修復** |
| **mabl** | Web/モバイル/APIに対応。オートヒーリング（自動修復）、失敗分析 |

共通する価値は**「UIが変わるたびにテストが壊れる」問題をAIで吸収する**こと。E2E自動化が続かない最大の原因がメンテナンス工数なので、そこを狙っている。

### 現場での割合（記事経由・原典未確認）

- 2025年時点で**81%のチームがテストにAIを導入**、うち**67%が「人間のレビュー付き」を条件**にしている
- テスト不安定率（フレイキーテスト）が10%を超えるチームは、安定しているチームよりデプロイ頻度が40%低い

### 公共案件で気をつけること

| 論点 | 注意 |
|---|---|
| 業務コード・仕様書をAIに渡してよいか | **案件のルール次第。参画後に必ず確認する**（情報持ち出しの扱いになる） |
| 生成物の責任 | AIが作ったケースでも、レビューして出した人の責任。「AIが作ったので」は通らない |
| エビデンス | AI生成の画面キャプチャ等は証跡として扱えない。実機の記録を残す |

Copilotの使い方の型は [copilot-playbook](../copilot-playbook.md) にある（項目7・8）。

## 5. 確認問題

**Q1.** 「テスト管理ツールを入れればExcelより効率が上がる」とメンバーが提案してきた。サブリーダーとして、賛成・反対の前に確認すべきことを3つ挙げよ。

<details><summary>答えの例</summary>

①納品物の形式（試験仕様書・結果報告書を契約上どう提出する決まりか）②お客様・協力会社を含めた閲覧者の範囲とアカウント・費用 ③既存ケースの移行コストと、移行中の二重管理期間。技術的な良し悪しより、**契約と関係者の制約**が先に効く。
</details>

**Q2.** AIにテストケースを作らせたら200件出てきた。そのまま試験仕様書に載せてよいか。

<details><summary>答え</summary>

だめ。①正常系に偏っていないか（[03-test-design](03-test-design.md) の異常系チェックリストで照合）②粒度が揃っているか ③期待結果が仕様から導かれているか（AIの推測が混ざっていないか）④件数が多いこと自体は品質ではない（重複・無意味なケースが混ざる）。**観点レベルで人がレビューする**のが最低条件。
</details>

**Q3.** E2Eの自動テストを「手動テストを全部置き換える」つもりで200ケース作った。半年後に何が起きるか。

<details><summary>答え</summary>

画面の変更のたびに大量に壊れ、修正が追いつかなくなる。壊れたテストが放置され「失敗して当たり前」になり、本物のバグも見逃す（フレイキーテスト問題）。だからピラミッド／トロフィーの考え方では**E2Eを薄く**する。置き換えるなら、下の層（単体・結合）から厚くする。
</details>
