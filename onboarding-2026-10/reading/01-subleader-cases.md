# サブリーダーの実例ケース集

day1 §0（サブリーダーの役割）の続き。§0の「5つの考え方」が、現場でどう使われるかを10のケースで見る。

ケースは公共系の更改案件・結合試験フェーズでよくある場面をもとにした**架空の典型例**。登場人物は次のとおり。

- **リーダー**: Pさん（判断する人）
- **自分**: サブリーダー（判断材料をつくる人）
- **メンバー**: Aさん（若手）、Bさん（年上のベテラン）、Cさん（中堅）

各ケースの読み方: まず「状況」だけ読み、**自分ならどう動くかを10秒考えてから**先を読む。

---

## ケース1: 初日、管理表が3種類ある

### 状況
参画初日。進捗はExcelのWBS、課題はRedmine、バグは別のExcelで管理されている。正直、Redmineに一本化した方が楽に見える。

### ありがちなNG
初週に「Redmineに一本化しませんか」と提案する。

### 考え方
**最初の2週間は変えずに観察する**（§0の5番）。3種類あるのには理由があることが多い。
- お客様への報告書がExcel形式で決まっている
- バグ表は品質報告の集計マクロとつながっている
- 前に一本化して失敗した過去がある

理由を知らずに変えようとすると、「分かっていない人」と見られ、その後の提案が通りにくくなる。

### 実際の動き
1. 3つの管理表を「何を・誰が・いつ更新し・誰が見るか」の表にまとめる
2. 分からないところだけPさんに聞く
   「バグ表がRedmineと別になっているのは、何か理由がありますか？ 運用を理解したいので」
3. 不便だと思った点はメモに溜める。2週間後にまとめて話す

### 学び
**提案は、現状の理由を理解してから。** 観察メモは、後で改善提案するときの根拠になる。

## ケース2: 「大丈夫です」の3日後に遅れが分かる

### 状況
Aさんに結合試験の機能Xを任せた。毎朝「進捗どう？」と聞くと「大丈夫です」。4日目の夕方、予定40件のうち12件しか消化していないと分かった。

### ありがちなNG
- 「なんで早く言わなかったの？」と責める
- 「大丈夫？」と聞き続ける（答えは「大丈夫です」しか返ってこない）

### 考え方
- **「大丈夫？」は、「はい」しか返ってこない質問。** 若手ほど言いにくい
- **数字で聞く**（§0の3番）、**状態を追う**（§0の4番）

### 実際の動き
聞き方を変える。

| NG | OK |
|---|---|
| 進捗どう？ | 今日は何件消化した？ 予定は何件？ |
| 大丈夫？ | 今どこで止まってる？ |
| 困ってない？ | 一番時間がかかってるのはどれ？ |

遅れが分かったら、責めずに状況を整理する。
「12件まで来てるね。残り28件で、残り3日。何が一番時間を食ってた？」
→ Aさん「テストデータの準備に毎回30分かかっていて…」

ここで初めて**原因（データ準備）**が分かる。対策（データ準備のスクリプト化、Cさんに手伝ってもらう等）をPさんに上げる。

### 学び
**進捗は自己申告ではなく、数字で毎日見る。** 遅れの原因は、本人を責めると出てこない。

## ケース3: お客様から「ついでにここ直して」

### 状況
結合試験の確認の場で、お客様の担当者から言われた。
「この一覧、並び順を納付日の新しい順にしてもらえますか？ 簡単ですよね」
確かに、コードは1行で直せそうだ。

### ありがちなNG
「分かりました、直しておきます」とその場で受ける。

### 考え方
- 公共系では、仕様の変更は**変更管理の手続き**（変更依頼・影響調査・承認）を通すことが多い
- 「1行で直せる」かどうかと、「直してよい」かどうかは別
  - 帳票や他画面と並び順がずれる
  - 試験済みの部分をもう一度試験する必要が出る
  - 契約の範囲外かもしれない
- お客様と直接やり取りしてよい範囲は、初日にPさんと決めておく（day1 §0）

### 実際の動き
その場ではこう返す。
「ご要望として承ります。影響範囲を確認して、リーダーのPからご回答します」

戻ったらPさんに上げる。
```
【事実】お客様○○様より、一覧の並び順を納付日の降順にしたいとの要望（口頭、本日の試験確認の場）
【影響（見立て）】画面1つの修正。ただし帳票△△と順番がずれる。試験済みケース8件の再試験が必要
【確認したいこと】変更管理の手続きに乗せるか。乗せる場合、起票は私が行います
```

### 学び
**「受ける／受けない」を決めるのはリーダー。** その場では即答しない。

## ケース4: 同じ種類のバグが5件続く

### 状況
1週間で、別々の機能から「日付が前日になる」バグが5件出た。担当者もバラバラ。

### ありがちなNG
1件ずつ担当者に直させて終わる。

### 考え方
- **担当者が違うのに同じバグ＝人ではなく仕組みに原因がある**（day2 §6 真因分析）
- 品質の数字の変化を、リーダーに早めに見せる

### 実際の動き
1. 5件を並べて共通点を探す
   → 全部、共通部品の日付変換を通っていて、タイムゾーンの指定が抜けていた（仮説）
2. 仮説を確かめる（共通部品のコードを読む、1件再現する）
3. Pさんに上げる
```
【事実】1週間で日付が1日ずれるバグが5件（機能A・B・D・F・G）
【見立て】5件とも共通部品の日付変換を経由。タイムゾーン未指定が原因の可能性が高い（1件で再現確認済み）
【影響】共通部品を使う残り12機能にも潜在している可能性
【対策案】①共通部品を修正し、12機能を再試験 ②当面は各機能で回避
【推奨】①（再試験の工数は約3人日の見込み）
```

### 学び
**1件の指摘を、そのクラス全体の指摘として扱う。** 数字（5件、12機能、3人日）で話すと判断が早い。

## ケース5: 年上のベテランに頼みにくい

### 状況
Bさんは経験20年のベテランで、自分より年上。Bさんの担当分が遅れている。どう伝えるか悩む。

### ありがちなNG
- 遠慮して何も言わない（遅れが放置される）
- 若手と同じ口調で「遅れてますよね」と詰める

### 考え方
- サブリーダーは**役割**であって、偉いわけではない。敬意は保ったまま、仕事として数字を確認する
- 経験のある人ほど、自分で原因と対策を持っていることが多い。**指示より相談**の形にする

### 実際の動き
「Bさん、機能Yの消化が予定より15件遅れていて、Pさんへの報告で見通しを伝えたいんです。Bさんの見立てだと、どのあたりで追いつけそうですか？ 何か手を回せることがあれば言ってください」

### 学び
**数字は遠慮しない。言い方は相手に合わせる。** 「報告に必要だから」と理由を添えると、角が立ちにくい。

## ケース6: リーダーと意見が違う

### 状況
遅れの対策で、自分は「Cさんを応援に回す」案、Pさんは「試験の後ろ倒し」案。自分の案の方が良いと思う。

### ありがちなNG
- Pさんの決定の後も、メンバーに「本当は応援の方が良かったんだけど」と言う
- 黙って従い、何も言わない

### 考え方
- **判断材料は全部出す。決まったら従う。**
- Pさんは、自分の知らない情報（お客様との約束、他チームの事情、予算）を持っていることがある

### 実際の動き
判断前に、比較を出す。
```
案① Cさん応援: 期限どおり。ただしCさん担当の機能Zが2日遅れる
案② 後ろ倒し: 機能Zは影響なし。全体の完了が3日遅れる
私の推奨は①です（機能Zは後工程に余裕があるため）
```
Pさんが②に決めたら、理由を聞いて理解する。メンバーには決定として伝える。

### 学び
**意見は判断の前に、数字と比較で出す。** 決まった後の陰口は、チームの信頼を一番壊す。

## ケース7: 自分が手を動かしすぎる

### 状況
メンバーが詰まっていると、自分で調べて直した方が早い。気づいたら自分の担当タスクも溜まり、管理表の更新が3日止まっていた。

### ありがちなNG
「自分がやった方が早い」を続ける。

### 考え方
- サブリーダーが手を動かしている間、**チーム全体の状態を見る人がいなくなる**
- メンバーが育たず、いつまでも自分に仕事が集まる

### 実際の動き
- 自分の実装・試験の担当は、全体の一部にとどめる（どれくらいかはPさんとすり合わせる）
- メンバーが詰まったら、**直さずにヒントを出す**
  「エラーの何行目？」「その前後のログは見た？」
- 30分考えて解けなければ一緒に見る、など**詰まったときのルール**をチームで決めておく
- 管理表の更新は、毎日決まった時間（例: 17時）にやる

### 学び
**自分の仕事は「チームが進む状態をつくる」こと。** 1人で10進めるより、5人が2ずつ進む方がよい。

## ケース8: 来週、試験環境を取り合いそう

### 状況
他チームの話から、来週は性能試験で試験環境が使われるかもしれないと聞いた。まだ正式な連絡は無い。

### ありがちなNG
正式な連絡が来るまで何もしない。

### 考え方
- これは**リスク**（まだ起きていない）。リスクは、起きる前に見せるのがサブリーダーの価値（day1 §3）
- 「噂の段階で上げるのは大げさ」と思わない

### 実際の動き
```
【リスク】来週、試験環境が性能試験で使われる可能性（他チームからの非公式情報）
【起きた場合の影響】当チームの試験が最大3日止まる
【確認してほしいこと】環境の利用予定を、Pさんから環境管理者に確認してほしい
【備え】使えない場合は、環境が要らない作業（試験仕様書の見直し、バグの再現手順の整理）を前倒しする
```

### 学び
**リスクは、起きた場合の影響と備えをセットで上げる。**

## ケース9: メンバーが体調不良で1週間休む

### 状況
Cさんが急に1週間休むことになった。Cさんの担当は残り30件。

### 実際の動き
1. Cさんの作業状態を確認する（体調に配慮し、無理に連絡しない。管理表・Redmine・共有フォルダで分かる範囲で）
2. 残作業を一覧にし、他のメンバーの空き状況と並べる
3. Pさんに上げる（**人に関わることは、必ずリーダーに上げる**）
```
【事実】Cさんが10/○〜10/○の1週間お休み。担当の残りは30件
【案】Aさんに15件、自分が15件。そのため私の管理業務を一部Pさんにお願いしたい
【または】Cさんの担当を後ろ倒しし、復帰後に対応（全体完了が2日遅れる）
```

### 学び
**人が抜けた穴は、作業の一覧と空き時間を並べると埋め方が見える。** 体調の話は、本人の同意なく広めない。

## ケース10: 定例会で何も言えない

### 状況
お客様との定例会に出ている。話が速く、気づいたら終わっていた。後でPさんから「何か気になったことあった？」と聞かれ、答えられなかった。

### 実際の動き
- **会議の前**: 資料を読み、気になる点を3つまでメモする
- **会議の中**: 決まったこと・持ち帰りになったこと・担当者・期限だけを書く。発言は「確認ですが、○○は△△という理解でよいですか？」の1回で十分
- **会議の後**: 当日中にPさんへ3行で送る（day2 §4）
```
決定: ○○は現行どおり
持ち帰り: △△の扱い（お客様が10/○までに回答）
気になった点: □□の件、お客様の説明と設計書の記載が違う
```

### 学び
**会議は、事前の3行メモと事後の3行報告でできている。** 最初から発言で目立つ必要はない。

## サブリーダーの1日（例）

| 時間 | やること |
|---|---|
| 9:00 | 昨日の消化数・バグ数を管理表で確認。気になる数字に印を付ける |
| 9:15 | 朝会。メンバーに「今日の予定件数」と「止まっていること」を聞く |
| 9:30 | 止まっていることの解消（環境、データ、仕様確認） |
| 10:00 | 自分の担当作業（試験、レビュー） |
| 13:00 | バグの分析・振り分け。同種のバグが無いか見る |
| 15:00 | お客様・他チームとの確認事項を回す |
| 17:00 | 管理表を更新。予実の差を確認 |
| 17:30 | Pさんへ報告（事実→影響→対策→お願い） |

---

## 報告の型（まとめ）

| 場面 | 型 |
|---|---|
| 遅れ・問題 | 事実 → 影響 → 原因 → 対策案（推奨つき）→ お願い |
| リスク | リスク → 起きた場合の影響 → 確認してほしいこと → 備え |
| 判断を仰ぐ | 案①・案②（それぞれの影響）→ 推奨と理由 → 期限 |
| 会議の後 | 決定 → 持ち帰り（誰が・いつまで）→ 気になった点 |

## 確認問題

**Q1.** メンバーから「たぶん明日には終わります」と言われた。どう聞き返すか。

<details><summary>答えの例</summary>

「残りは何件？ 今日は何件進んだ？」と数字で聞く。「たぶん」は根拠が無いサイン。今日の消化ペースで残りが明日に収まるかを、一緒に計算する。
</details>

**Q2.** ケース3で、お客様が「Pさんには自分から話しておくので、先に直してください」と言った。どうするか。

<details><summary>答えの例</summary>

それでも直さない。「ありがとうございます。念のため私からもPに共有し、手続きが済み次第対応します」と返す。お客様がPさんに話したかどうかを確認できず、手続きが漏れる原因になる。
</details>

**Q3.** ケース1〜10のうち、明日から一番使いそうなものを1つ選び、「どの場面で・何と言うか」を1行で書け。

<details><summary>考え方</summary>

正解は無い。ポイントは、場面とセリフまで具体的にすること。例:「朝会で、Aさんに『今日は何件の予定？止まってることある？』と聞く」。
</details>
